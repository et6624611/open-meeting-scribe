# ROADMAP — 版本路线

> 渐进构建：先跑通最小链路，再叠加能力。呼应 MISSION「本地优先」长期方向。

## v1 · 云方案（当前）
**目标**：最快跑通「音频 → 纪要」，验证产品价值。
- ASR + 分离：DashScope `paraformer-v2`（云）
- 纪要：通义千问 `qwen-plus`（云）
- 采集：文件输入 + BlackHole 内录
- 界面：FastAPI 本地 Web UI
- 里程碑：P0 环境 → P1 CLI 链路 → P2 Web UI + 内录
- 依据：[ADR-0001](adr/0001-mvp走云方案.md)

## v2 · 本地兜底
**目标**：离线场景保底录音采集，联网后再完成识别与纪要生成。
- 本地仅负责录音采集与存储（复用 BlackHole 内录 + WAV 落盘）
- 识别、说话人分离、LLM 纪要生成均待联网后调用云端处理

## v3 · 声纹姓名化 ✅
**目标**：把「说话人1」变「张三」。
- 初版用 resemblyzer 提取 256 维声纹嵌入向量（GE2E 编码器，英文语料训练，判别力有限，需 cohort centering 补丁）
- 声纹注册表持久化（`data/voiceprint_registry.json`）
- 转写后自动匹配已注册说话人，无匹配时降级为手动绑定
- 说话人管理页显示声纹状态，支持注册/更新声纹

## v4 · CAM++ 声纹编码器升级 ✅
**目标**：把 GE2E 换成中文语料训练的 CAM++，抬判别力天花板，清掉旧版补丁。
- 编码器：CAM++（FunASR CAMPPlus 实现，ModelScope `iic/speech_campplus_sv_zh-cn_16k-common` 权重，28MB）
- 嵌入维度：256 → 192（L2 归一化）
- 注册表加 `model_version` 字段（当前 `cam++-v1`），旧版本记录匹配时自动忽略
- 移除 cohort centering / RAW_* 双阈值等 GE2E 时代的补丁代码
- **匹配算法升级**：逐人独立匹配 → per-meeting 统筹分配（中心化消除同会议信道公共分量 + 匈牙利算法保证一对一），接受准则改为仅看 margin
- 依赖：`resemblyzer` → `torch` + `torchaudio`
- 迁移脚本：`scripts/backfill_voiceprints.py` 全量重建注册表
- 评测：6 人会议对比测试，0 误识（旧方法虽 sim 高但含信道偏置，新方法更可靠）

## v3+ · 说话人分离精度增强 ✅
**目标**：解决本地 MFCC 聚类精度低、批管线 speaker_count 传递不完整导致的分离质量瓶颈。

### 短期（参数调优 + 链路补全） ✅
- **S1** ✅ `speaker_count` 全链路传递：文件上传路径增加自动估算（归一化→均匀采样→钳制到 1-10），前端可选手动指定
- **S2** ✅ 本地聚类人数下限保护：估算值钳制到 [1, 10]，避免噪声产生过多伪说话人
- **S3** ✅ 放松 `correct_speaker_ids` 后处理修正条件：夹心修正间隔 2000ms→800ms，碎片跟前句间隔 2000ms→500ms
- **S4** ✅ 聚类参数调优：相似度阈值 0.70→0.65（更严格区分），特征窗口 2s→1.5s（提升时间分辨率）

### 中期（特征升级）
- **M1** ✅ 实时聚类特征方案确定：曾升级至 CAM++ 192 维嵌入，后因云端拆分（v5）回退为 MFCC 14 维（实时侧纯本地，无 torch 依赖）
- **M2** 引入上下文连续性先验：相邻句子倾向同一说话人，减少跳变
- **M3** 自适应阈值：基于说话人间相似度分布动态调整聚类阈值

### 长期（混合方案）
- **L1** 批处理结果反向校准实时聚类参数，形成「实时粗估→批处理精修→参数回写」闭环
- **L2** 谱聚类（Spectral Clustering）替代在线贪心聚类，实现全局最优分割
- **L3** 声纹注册表辅助批处理修正：已注册说话人的声纹用于后处理验证/纠正 speaker_id

## v1.x · 会议纪要顶部菜单精简
**目标**：顶部菜单要克制，更多信息留给内容而不是功能。这是软件的设计范式。

## v1.x · AI 对话面板消息类型增强
**目标**：AI 面板从「纯文本气泡」升级为「过程可见、结果可操作」的 Agent 交互，让用户看得到系统在做什么，且 AI 产出可直接操作。

### 现状
AI 面板消息流目前只有纯文本气泡；工具调用过程、结构化结果、原文引用等 Agent 信息缺失，无法体现对话驱动操作的产品定位。

### 消息类型规划（按优先级）
- **P0 · 工具调用卡片**：AI 调用后端工具（转写/纪要生成/待办提取）时展示过程卡片——可折叠，完成后收起为一行摘要；显示耗时；失败变红并提供重试按钮
- **P0 · 结构化结果卡片**：待办/结论渲染为可操作卡片——待办项可勾选、可导出到日历；结论项可引用跳转转写原文；支持一键复制
- **P1 · 上下文引用块**：AI 回答涉及会议内容时显示引用来源（说话人 + 时间戳 + 原文摘录），点击跳转转写面板对应位置，可选播放原声
- **P1 · 进度指示器**：长任务展示分阶段流水线状态（✓ 已完成 / ⏳ 进行中 / ○ 待执行 + 各阶段耗时），降低排队焦虑
- **P2 · 快捷指令结果预览**：`/待办` `/结论` 等快捷指令返回结构化卡片（标题 + 要点列表 + 展开详情 / 导出 Markdown）
- **P2 · 侧边栏会话列表增强**：列表卡片增加对话轮数、待办数量、最后一条摘要（悬停显示）、后台任务完成未读标记

### 依赖与约束
- 结构化结果卡片、进度指示器依赖后端暴露细粒度的任务阶段事件（现有轮询接口可能需要扩展）
- 上下文引用块需要转写原文的句级时间戳数据（转写结果已含），并与转写面板建立双向导航

## v1.x · 会议纪要归档到项目文件夹
**目标**：让会议纪要成为项目资料的有机组成部分，以 AI 工具友好的结构化格式归档到项目目录下，使 AI IDE（Qoder、Cursor 等）的 Agent 在扫描项目文件时能快速理解会议上下文——讨论了什么、决定了什么、要做什么。

### 背景
当前会议纪要仅存储在本应用的 `data/tasks/` 目录中，虽然通过 `project_id` 关联了项目，但产出内容对外部工具不可见。用户希望会议纪要能以结构化 Markdown 文件的形式落入项目文件夹，与项目文档并列，形成完整的知识资产。更关键的是，这些文件需要被 AI 编程助手（如 Qoder）在分析项目时自动发现和解析，让 AI 能立即理解项目的决策历史和行动项。

### 核心设计

#### 1. 项目设置：是否允许归档
- 项目数据模型新增 `meeting_archive` 配置项：
  ```json
  "meeting_archive": {
    "enabled": false,
    "subfolder": ".meetings",
    "format": "summary"
  }
  ```
- `enabled`：总开关，默认关闭。用户需显式开启才写入
- `subfolder`：归档子目录名（相对于项目文件夹根路径），默认 `.meetings/`（以 `.` 开头避免干扰正常文件浏览）
- `format`：归档内容粒度
  - `summary`：仅纪要摘要 + 待办
  - `full`：摘要 + 章节 + 待办 + 转写原文
  - `minimal`：仅摘要

#### 2. AI 工具友好的文件格式规范

**设计原则**：文件同时服务于「人类阅读」和「AI 快速解析」两个场景。AI Agent 通常先扫描 Front Matter 判断文件相关性，再按需读取正文。格式必须标准化，让任何 AI 工具无需猜测结构。

**文件命名**：`{meeting_date}_{title}.md`（如 `2026-09-06_财务星瀚需求对齐.md`）

**Front Matter（YAML）**：AI Agent 的第一眼判断依据
```yaml
---
title: "财务星瀚需求对齐"
description: "与财务团队对齐星瀚系统全面预算模块的技术方案，确认接口规范和数据迁移策略。"
type: meeting
created_at: "2026-09-06"
meeting_date: "2026-09-06"
duration_minutes: 45
participants: ["张三", "李四", "王五"]
task_id: "abc123"           # 回溯到本应用的完整数据
tags: ["财务", "预算", "技术方案"]
category: "technical"
status: "published"
# AI 快速摘要——Agent 仅读此字段即可判断是否需要深入
ai_context: "确认了星瀚预算模块采用 RESTful API 对接，数据迁移分三期完成，首期处理历史科目映射。张三负责接口文档，李四负责迁移脚本。"
---
```

**正文结构（固定章节，AI 可按 section 精准提取）**：
```markdown
## 摘要
（一段话概括会议核心结论）

## 关键决策
- **决策 1**：采用 RESTful API 对接星瀚预算模块
  - 依据：团队熟悉度高，维护成本低
  - 反对方案：gRPC（性能优势在当前规模下不明显）

## 行动项
<!-- 结构化 action items，AI 可直接提取为待办 -->
- [ ] @张三 输出接口文档 — 截止 2026-09-10
- [ ] @李四 编写数据迁移脚本 — 截止 2026-09-15
- [x] @王五 确认科目映射规则（已完成）

## 讨论要点
### 议题 1：接口规范
（讨论细节...）

### 议题 2：数据迁移策略
（讨论细节...）

## 相关信息
- 关联项目：财务星瀚项目
- 参考资料：`docs/API_CONTRACTS.md`
```

**为什么这样设计**：
- `ai_context` 字段：AI Agent 仅扫描 Front Matter 即可获得会议全貌，无需解析全文。这是最关键的优化——类似于代码文件的 JSDoc/docstring，让 AI 在文件索引阶段就能判断相关性
- 固定章节标题：AI 可按需跳转（只读「关键决策」或只读「行动项」），降低 token 消耗
- `type: meeting` 标签：让 AI 工具立即识别文件类型，区别于技术文档、设计文档等
- 行动项使用 Markdown checkbox 语法：GitHub/IDE 原生渲染，AI 可直接提取为 TODO
- Front Matter 遵循项目已有的 Metadata.md 规范（title/description/tags/category 等必填字段），与项目其他文档风格一致

#### 3. 归档触发时机
- 纪要生成完成后，若项目开启了归档，自动写入
- 支持手动触发：详情页增加「归档到项目」按钮，可单独操作
- 纪要重新生成时，覆盖同名归档文件

#### 4. 多文件夹项目的归档策略
- 归档到项目的**第一个**关联文件夹下（主文件夹）
- 若项目无关联文件夹，归档功能不可用（UI 置灰并提示）

### 实现要点
- **数据层**：`core/projects.py` 新增 `archive_meeting_note()` 函数，负责组装 Markdown 内容（含 Front Matter + 固定章节正文）并写入目标路径
- **模型层**：`projects.json` 项目数据新增 `meeting_archive` 字段；`ProjectUpdate` 模型扩展支持更新该配置
- **API 层**：`PUT /api/projects/{id}` 支持更新归档设置；新增 `POST /api/projects/{id}/archive` 手动触发单次会议归档
- **前端**：项目设置区域增加「会议纪要归档」开关 + 子目录名 + 格式选择的配置 UI
- **幂等性**：同一会议多次归档覆盖同一文件（通过 task_id 映射文件名），不产生重复

### 约束与风险
- 写入用户本地文件夹需做好异常处理（权限不足、磁盘满、路径失效）
- 归档文件不应被项目索引扫描纳入（`.meetings/` 目录需加入 `EXCLUDED_DIRS`），避免自我引用循环
- 删除项目时不自动删除已归档的会议纪要（用户的项目资料不应因本应用操作而丢失）
- `ai_context` 字段需要 LLM 额外生成一次（约 50 token），可复用纪要生成时的输出，不增加额外 API 调用

## v5 · 声纹云端拆分 ✅
**目标**：将 CAM++ 声纹推理从主项目剥离，部署为独立云端服务，主项目彻底去掉 torch 依赖，为 Windows 打包瘦身。
- **云端服务**：CAM++ 192 维嵌入提取部署至 47.116.10.194:8100（systemd 自启，RESTful API）
- **Provider 抽象层**：`core/embedding_provider.py` 统一接口，云端优先 → MFCC 降级
- **主项目清理**：删除 `LocalCamPlusProvider`、`extract_embedding_local()` 等本地 CAM++ 代码
- **依赖瘦身**：`requirements.txt` 移除 `torch` + `torchaudio`（~2GB → 0）
- **实时侧**：`core/diarization.py` 纯 MFCC 聚类（numpy + scipy），无 torch
- **配置**：`data/settings.json` 新增 `voiceprint` 配置节（provider / base_url / api_key）
- **兼容性**：云端 `cam++-v1-cloud` 与本地 `cam++-v1` 声纹注册表互相兼容
- 依据：[ADR-0009](adr/0009-声纹识别服务云端拆分.md)
