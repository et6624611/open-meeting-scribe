## 1. 前置说明：设计体系口径

按工单要求先判定实现口径，避免给出无法落地的建议：`frontend/package.json` 依赖为 `vue 3.5 / pinia / vue-i18n / vue-router / axios / mermaid / vue-virtual-scroller`，**无 Spark Design、无 Element Plus/Naive UI、无 Tailwind，仓库内不存在 `components.json`**。真实 UI 是手写 SFC + `<style scoped>` + CSS 自定义属性；原型的 `--accent/--subtle/--warn` 令牌命名与真实代码同源。

因此本意见书的所有建议均以 **「Vue 组件 + CSS 设计令牌 + role/aria 语义」** 表述，不引用任何组件库组件名。若 OPS 后续引入组件体系，§3–§4 的每条建议都可直接映射（分段控件 / 状态标签 / 对话框 / 警告条），不影响结论有效性。

## 2. 逐条评审

### R1 · 决策层与详情层的层级、密度 —— 修改建议

**现状事实**：③ 的两卡（`#c-local` / `#c-cloud`）与六张详情卡同处一个 `.card` 容器内，两层之间仅靠一个 `<h3>`（PROTOTYPE:440）分隔；六张详情卡用 `.sub-grid`（`auto-fit / minmax(240px,1fr)`）平铺，视觉权重完全相同。

问题在于这六张卡承担三种不同角色，被压成了同一层：

| 角色 | 卡 | 交互性 |
|---|---|---|
| 默认值来源 | 账户 · 套餐 | 可写（登录态、配额、`优先使用体验`） |
| 决策落点 | LLM · 算力来源 / ASR · 算力来源 | 可写（联网态） |
| 状态回显 | 引擎 · 本地组件 / CLI 引擎 / 使用面回显 | 只读 |

**修改建议（具体到组件与状态）**

1. **两层分离**：决策层与详情层拆为两个容器，详情层用内缩 + 次级底色（`--bg` 上再叠 `--surface`，或 `border-left: 2px solid var(--accent-mid)` 的引用轨）表达「从属于上方选中的卡」。仅靠 `<h3>` 无法承载层级。
2. **补「本机链路接管」的卡级置灰**：`renderDetail()`（PROTOTYPE:697-712）当前只做 `sel.disabled = off`，浏览器默认灰度只作用在 `<select>` 一个控件上，整张卡其余内容（标题、计费行、只读徽章）毫无变化。建议离线态给 LLM/ASR 两张 subcard 加 `.is-inherited` 态：标题右侧一枚「本机接管」锁形徽章 + 正文降透明度，比 disabled 控件更能表达"这里不是不能点，是归上面管了"。
3. **离线态下账户开关必须置为不可影响**（**演示自相矛盾，必改**）：`setPsub()`（PROTOTYPE:645-652）在 `FIX.mode==='local'` 时仍把 LLM/ASR 切回 `trial` 并弹出「账户勾选生效：LLM/ASR 详情已显式切回体验配额并标注『默认生效』」，但同一函数末尾的 `renderDetail()` 因 `isDefault = ... && !off`（:710）**根本不会渲染那枚徽章**。即：界面宣称了一件界面自己没做的事——这正是 ① 页诊断的缺陷类别在建议层复现。修正：离线态下 `sw-psub` 置 disabled + 说明文案「离线模式下本设置暂不生效」，不弹成功反馈。
4. **因果联动不要只靠徽章**：账户勾选 → 详情默认值的可见表达需要三件套（缺一不可）：(a) 详情卡上「默认生效（来自账户勾选）」徽章；(b) 徽章可点，点击滚动并高亮账户卡的对应开关；(c) 勾选变化时两条详情行做一次性变化提示（150ms 背景渐隐，不用 toast）。当前只有 (a)，且 (a) 的样式复用了 ① 页的 `.draftchip`（PROTOTYPE:711 仅覆写配色）——评审现场容易把「默认生效」误读为 ① 的「未保存草稿」。**新增独立语义样式** `--badge-default-effective` / `--badge-override`，不要复用草稿态 class。
5. **补「已覆盖」持久态徽章（当前设计缺失）**：第 5 刀承诺「逐能力覆盖后持久化覆盖状态，不被下次登录/勾选改回」（PROTOTYPE:501）。但界面上一旦用户改选自带 Key，徽章只是**消失**——于是"用户显式覆盖过"与"从没配过"在界面上长得一样，恰恰无法证明该承诺。建议三态：`默认生效（账户）` / `已覆盖（本能力）` / `未设置`。这一条是裁决落地的必要条件，不是润色。
6. **补 access_mode=null 的未选态**：① 页批评真实代码「用户只见三张无选中的卡，没有任何必须选一个的提示」（:217）。③ 的初始态 `FIX.mode=null` 同样是两张空白卡 + 点当前卡才给反馈，未演示修复。建议：未选态下两卡之间上方一条强引导条（`banner info` + 主操作「先选一个」），并在联网卡副标题上标注「需登录」。

**需项目方裁决（新增）**：离线模式是否允许 **LLM 单项走本机端点（Ollama）** 之外的例外？现有 `amc` 文案写「算力全在本机 · 数据不出设备」，而详情层允许联网态下 LLM=本机端点 —— 顶层语义与下层配置存在双向例外，需明确顶层卡的措辞上限（连带影响 R6/Q1）。

### R2 · 能力级算力来源选择器 —— 修改建议

**选项命名**（`#sel-llm` / `#sel-asr`，PROTOTYPE:456-468）：

1. 单个 option 里塞了三件事——计费概念 + 传输方式 + 模型名：`体验配额（平台代理 · qwen-plus）`。option 是选择器，不是状态面板。建议 option 文案只留 `体验配额` / `自带 Key` / `本机端点`，模型名与传输方式移到选择器下方的就绪态行（`#llm-ready` 槽位）里呈现。
2. **规格语言泄漏进用户文案（必改）**：`自带 Key（DashScope / OpenAI / DeepSeek / 预设见 ②L1）` 与就绪态 `✓ Key 就绪（编辑入口唯一保留在「服务」L2，一处显式保存）` 里的「②L1」「L2」是原型页号，真实产品不存在。生产文案应替换为动词化链接：`管理供应商预设` /`去「服务」页修改`。
3. **不可用态缺 CTA**：`✗ 未配置 API Key → 卡片状态栏常驻此警告，直达服务页`（:694）与 `✗ 未登录：体验配额不可用（登录门槛）`（:687）都只有文字，没有任何可点元素，文案里的"直达"在界面上不成立。建议每类不可用态配一个行内 `btn sm`：`去配 Key` / `去登录`，与就绪态同行右对齐。
4. **就绪/警告的行内呈现要满足对比度**（详见 R3 第 4 条）：`.ready-warn` 用 `--warn #b06f00` 压白底实测 **4.10:1**，`.warn on --warn-soft` **3.72:1**，均低于 11–12px 小字所需的 4.5:1。状态色需加深（建议 `#8a5800` 一档）或改为「色块 + 图标 + 正文用 `--text`」三通道，不能只靠颜色。
5. **与 L2「服务」编辑面的空间关系**：方向正确（来源选择留详情层，Key/Base URL 编辑唯一收敛到服务页），但当前详情卡只给了一个"去服务页"的隐含承诺。建议 LLM/ASR 两张 subcard 底部固定一条**编辑轨**：`当前 Key：sk-a***3（脱敏）· 上次更新 09-21 · [在服务页编辑]`，让「唯一编辑面」在视觉上有出口，否则用户仍会本能地在卡上找输入框。

### R3 · 专家详情 = 注释层的视觉语法 —— 修改建议

**方向通过**（注释层而非平行界面，与「同模型加细节」一致），但落地有三处不足：

1. **注释层只覆盖了一半**。`body.expert .amc .tech{display:block}`（PROTOTYPE:80-81）只作用于两卡标题下方，六张 subcard 在专家态毫无变化；而第 2/6 刀写的是「服务/引擎页出现底层字段」。于是 ③ 演示的"加细节"实际只加在决策层，评审会看不到详情层的注释语法。**建议**：专家态给每张 subcard 增加同一槽位——`.tech` 等宽注释行（`asr.mode=direct`、`llm.provider=DashScope`、`chat_engine.auth_tier=readonly`），样式与卡片注释完全一致，用同一套语法证明"这是同一模型多一层"。
2. **技术注释与用户注释必须可区分**：`engine.mode=local · asr.mode=local` 用 `--subtle` 灰、`10.5–11px` 等宽，与「备注/说明」的 `.note` 同色同量级，专家扫一眼分不出"这是可核实的工程事实"还是"这是编辑写的话"。**建议**：注释层统一 `font-family: --code` + 前置 `>` 或键值对齐（`engine.mode ▸ local`），并与 `.note` 拉开至少一档字号（注释 ≥12px，说明 12px 但非等宽）。
3. **注释不能成为"更浅更小"的同义词（无障碍硬指标，必改）**。实测：`.tech` = `#8a93a2` on `#f2f4f7` → **2.81:1**，连 3:1（大字号 AA）都不达标；`.note` = `#8a93a2` on `#fff` → **3.10:1**。而注释层恰恰是专家唯一需要逐字读的内容（工程值写错=用户判断错）。**规范建议**：注释层最低 12px + 对比度 ≥4.5:1（`--subtle` 至少加深到 `#6b7382` 一档），等宽 + 降饱和可以，降对比不行。这条应作为产品级规则写进需求单，不只对本页生效。
4. **专家开关自身的语义，与 ① 页的指控冲突**：① 用整整一节批评真实代码「`role="switch"` 装在 `role="radiogroup"` 里、`tabindex` 不一致、箭头键无响应」（:207）。但 ③ 的两个卡是 `<div onclick>`（PROTOTYPE:427/432，无 `role`/`tabindex`/`aria-checked`），三个开关是 `<div class="sw" onclick>`（:424/444/450，无 `role="switch"`、无 `aria-checked`、键盘不可达）。**评审会现场用 Tab 走一遍 ③ 会直接暴露。** 建议演示版就补齐：`div.amc-grid[role=radiogroup]` + `div.amc[role=radio aria-checked tabindex]` + roving tabindex（←/→ 在两卡间循环），`div.sw[role=switch aria-checked tabindex=0]`，弹窗见 R4。
5. **开关位置**：`.switchrow` 在决策卡的容器内右上（:422-425），视觉上像"两张卡的属性"。工单/裁决口径是**页面级**开关，建议移出卡片，置于视图标题行右侧，并加一句注释层作用范围说明（"开启后：卡片、详情卡、流向矩阵同步显示工程值"）。

### R4 · 后果预览弹窗 —— 修改建议

**说服力判断：对 ① 页"一次点击全改"的反差是成立的**——`pick()`（PROTOTYPE:659-670）强制二次确认并列出后果，对比 :206 现状的静默早退，这一组并排演示有效。但信息结构缺三块：

1. **缺"将被改写的投影字段"清单**：工单 R4 明确关注「将改写投影字段 / 进程动作 / 计费提示」三类，演示只覆盖了后两类。`impact` 数组（:663-667）全是自然语言，没有字段级 diff。建议弹窗正文固定三段：
   - `字段变更`：`access_mode: null→local`、`engine.mode: proxy→local`、`asr.mode: 保持 direct`（三列：字段 / 现值 / 将写入）；
   - `进程动作`：`启动本地引擎子进程`、`停止云端会话`；
   - `计费与出网`：`无出网` / `LLM 走你的 DashScope Key`。
   字段段与专家开关联动（专家关闭时折叠为"查看技术细节"），这样同一个弹窗同时服务两类用户，不破坏 R3 的"同一模型加细节"。
2. **确认节奏建议**：切换接入方式会启停子进程 + 改写多个投影字段，属高影响操作，**一次显式确认合适**，不建议加二次勾选（会变成"无脑点确认"）。但需要：主操作按钮文案具体化（`确认切换并启动本机引擎`，而非通用`确认切换`，:552）；取消是默认焦点；弹窗期间背景内容不可交互。
3. **缺失败与回滚态**：`confirmPick()`（:672-681）只有成功路径。真实切换可能因模型未装、引擎启动失败而半途而废——而"半途而废"正是 ① 页双写问题的另一副面孔（`access_mode` 改了、`engine.mode` 没改）。建议弹窗内加 `切换中 →（失败）未生效，已保持原模式` 的显式失败态，并把"是否回滚"上升为裁决项（见下）。
4. **点当前卡的反馈已修对**：`msg('info','已是当前模式…')`（:660）修掉了现状静默无响应，通过。建议生产实现升级为非阻断 inline 提示，与 ① 的批评保持一致。

**需项目方裁决（新增 2 条）**
- **裁决-1**：切换失败时的语义——全量回滚到切换前状态（推荐：符合"一个逻辑状态一个真相"的收敛目标），还是允许部分生效？此项直接决定需求单的事务边界，不属 UI 可自裁。
- **裁决-2**：`联网 → 离线` 是否需要比 `离线 → 联网` 更强的确认（离线方向要停进程/断当前云端会话，可能打断正在进行的转写）。当前两向文案对称，但风险不对称。

### R5 · ① 页诊断叙事的呈现质量 —— 修改建议（含 1 处必改事实错误）

动线整体有效（现状→下钻→建议），且证据密度足。四处建议：

1. **【必改 · 事实错误】问题 2 的演示与真实代码相反。** 弹窗断言「配置矛盾：声纹 provider=cloud，实际会出网，界面仍在向你保证『零出网』」（PROTOTYPE:185），但 `core/embedding_provider.py:520-533` 的选择优先级第 0 档是：`provider_mode == "local" or _local_engine_active()` → **强制走本机 CAM++，CAM++ 未就绪则直接降级 MFCC，代码注释自述「本地模式下绝不触达云端（零出网）」**。而演示左侧正是"离线卡 + provider=cloud"的组合。开发者现场翻一个函数即可推翻，整页可信度连坐。

   **可保留同一结论的更正讲法（三条均已核实，比原指控更有力）**：
   - (a) 「零出网」在离线档**为真，但只因为文案与实现无绑定**——`settings.json:167` 是写死字符串，不读任何字段。今天恰好成立，任何一次改动都能悄悄破坏它。这是**信任的结构性缺陷**，而不是当下正在发生的欺骗，恰好支撑第 4 刀「从派生校验升级为结构性为真」；
   - (b) 同时 `voiceprint.provider` 在离线档是**死字段**（被 `:520` 短路忽略），它本身就是"四个写入口"的又一例，比原演示更贴 W1 根因；
   - (c) 云端声纹在 **hosted/proxy 档确实出网**（i18n `settings.json:275` `engine_cell_voiceprint_proxy`「音频片段送云端声纹服务」），且本机运行时 `data/settings.json` 当前默认 `voiceprint.provider="cloud"`（含真实 base_url/api_key；该文件已列入 `.gitignore:16`，非入库泄露问题，但可证默认态即出网）。
2. **【建议 · 引用规范】① 页「问题 3」三套词汇表的行号指向需补全文件名。** 第二、三列只写 `:237-240` / `:256-259`，实际指向 `frontend/src/i18n/locales/zh-CN/settings.json`（`engine_mode_*` 与 `engine_col_*` 文案，内容完全对得上，含幽灵枚举 `engine_mode_cloud`）；而同一份原型在 ②L2 把 `SettingsView.vue:237-241` 标为 ASR 下拉——**同一段行号在两个文件里各有其义，现场查 SettingsView.vue:237 会查错**。真实引擎下拉在 `SettingsView.vue:340-344`，矩阵渲染在 `:434-456`（`:1041` 是脚本常量）。建议：所有标注统一 `文件:行`，并区分**文案位置（i18n）**与**渲染位置（.vue）**两类引用；`矩阵列头` 应为 `i18n:254-259`（现写 256-259 漏了 local 列）。
3. **证据层与主张层混排**。② 页头部声明"忠实复刻 main 分支实际渲染的字段"，但 L5 右卡是「建议：配置面↔使用面闭环」（:398）、L0 的 `tierName()` 是**未来风险**（付费档接入后才说谎）而非当下缺陷、L3 的 warn 条混入裁决结论。建议在 ② 内给每个块加 `【现状】/【建议】/【未来风险】` 三选一 chip，严重度分层，否则证据页会被"你也夹带了主张"削弱。

### R6 · 词汇收敛落地检查 —— 通过（方向）+ 修改建议

四词主口径（离线 / 联网 / 体验配额 / 自带 Key）在 ③ 的**卡片标题与主选择器上基本成立**，方向通过。落地检查发现三处偏差：

1. **四词覆盖不住实际决策空间，需扩为五词**：裁决② 后 LLM 有三选（体验 / 自带 Key / **本机端点**），ASR 两选。「本机端点」已是用户必须理解的第四种算力归属，不可能全部塞进括号注释。**建议词表：离线 / 联网 / 体验配额 / 自带 Key / 本机端点**，其中「本机端点」仅出现在 LLM 详情层，不上顶层卡。
2. **一词多形（需收敛，均为原型内自相矛盾）**：
   - 「本机端点」（`#sel-llm` option）vs「自接端点」（矩阵列头 `labels.byok='自带 Key / 自接端点'`，:724）——同一事物两个名字；
   - 「平台代理」（option 与矩阵列头）是**第五个词**，却出现在用户可见标签而非专家注释位——违反第 3 刀自己定的口径。建议矩阵列头改 `体验配额（平台代理）`→`体验配额`，proxy/cloud/direct 只在专家注释行出现（:725 的 `tech` 已做对，照此统一）。
3. **「云端」承担两义，会撞车**：③ 声纹块写「云端已下架」（指**能力**），同页联网卡写「算力在云」（指**模式**），相邻读起来像自相矛盾。建议：能力侧一律写「云端声纹提取已下架（不再有云端路径）」并挂 `green` 完成态标签；模式侧避免裸用"云端"作名词。
4. **矩阵粒度不足以承载新模型（连回 R1 裁决项）**：三列（local/trial/byok）承载不了四种归属。当 `联网 + LLM=本机端点` 时，`llmCol` 被判为 `byok`（:728），于是"上下文不出网"的那一行高亮到列头写着「自接端点/直连你配置的云服务」的列——**矩阵把零出网行标成了云列**，这是 ① 问题 2 同类错误（界面保证了一件不成立的事）在建议层的复现。建议矩阵单元格内加出网性标记（`零出网` / `出网`）或为「本机端点」单列。

## 3. 待裁决项的设计立场

### Q1 · 顶层命名：建议定名「**联网模式**」，否掉「在线模式」，慎用「云端模式」

判据（建议作为卡片命名的通用规则）：**顶层卡的标题必须写「不会被下层配置证伪」的判据**。理由是本页的全部病根就是"界面写了一句实现可以推翻的话"（`settings.json:167`），命名若重复这个错误模式，等于在新架构里埋第二个同类缺陷。

| 候选 | 与「离线」的对偶性 | 证伪风险 | 结论 |
|---|---|---|---|
| **联网模式** | 离线/联网 是中文里最强的一对 | 低：只要任一能力走云即为真；`LLM=本机端点 + ASR=体验` 时仍为真 | **推荐** |
| 云端模式 | 与「本机/本地」对偶更自然，且直说算力位置（卡的副标题"算力在云"） | **高**：`联网 + LLM=本机端点 + ASR=体验` 时，LLM 不在云上，卡名被下层配置证伪；且与「云端声纹已下架」字面撞车 | 不推荐 |
| 在线模式 | 对偶最强 | 高：与**登录态**（同页账户卡就写"已登录/未登录"）和**网络连通性**三重歧义 | 不推荐 |

代价与补偿：「联网」说的是手段不是收益，价值感弱于「云端」。补偿方式已由卡片副标题承担（"算力在云 · 计费来源在下方详情逐能力选择"），建议副标题保持"收益在前、可配性在后"的顺序，不要改标题。**GLOSSARY 清退建议**：「托管」保留一条历史映射注记（存量 `access_mode=hosted` 迁移要用，见迁移表），但从用户可见文案全量清退。

### Q3 · 配额耗尽的明示降级提示样式：三级分层，用 amber 不用 red，文案禁现「降级」

原型当前把它做成能力 subcard 内一行 12px 文字（`#llm-ready`，:689），而这行文字自己写着「横幅常驻」——**样式与文案不符**。建议：

| 层级 | 位置 | 样式 | 内容与生命周期 |
|---|---|---|---|
| L1 行内状态行 | 该能力 subcard 就绪态槽位 | `--warn` 深色文字（加深至 ≥4.5:1）+ ⚠ 图标 + 行内主操作 `[改选]` | **常驻**，与「✓ 可用 · 剩余 xx 分钟」占同一槽位，位置稳定不跳动 |
| L2 页面级横幅 | 决策层上方，全宽一条 | `banner warn`（`--warn-soft` 底），**不用 `--err`** | 首次发生可见；用户点「知道了」后**折叠为一行历史**，不消失；恢复额度后转为灰色事实条 |
| L3 顶层卡角标 | 联网卡右上 | 数字角标（"1 项能力已自动改用"） | 让 L0 决策层能感知 L2 详情层状态，避免用户以为整体没事 |

理由与设计规则：
- **不用红色**：降级是系统按规则正常兜底，不是故障。`--err` 会引导用户去怀疑自己的 Key 坏了，反而增加错误操作与工单。红色留给"出错了 / 可能丢数据"。
- **必须点名能力**：降级是**逐能力**的（LLM 可能耗尽而 ASR 还有额度），单条全局横幅不写能力名会产生"我的额度到底怎么了"的二次歧义 → 文案主语固定为 `LLM` / `ASR`。
- **三段式文案，禁工程词**：`发生了什么` → `现在的行为（含账单归属）` → `下一步`。示例：

  > **LLM · 体验配额已用尽** · 本次起 LLM 改用你的 DashScope Key 计费（`sk-a***3`），ASR 不受影响。 [改回体验配额] [查看用量]

  「降级 / 兜底 / fallback / route_override」一律不上界面——与第 3 刀"清理静默语义"同源：让用户看见的是**换了计费方**，不是**系统做了个内部决定**。用户词建议定「**自动改用**」。
- **不留 toast**：与第 5 刀一致（`App.vue:238` 的事后 toast 降为兜底）。计费归属变更属信任级信息，必须可复读；toast 不可复读。
- **每次自动改用落一条本地事件记录**（账户卡下"近期变更"折叠区即可），因为直接关联账单争议；这条也顺带把第 5 刀"覆盖状态持久化"变成界面可证明的东西（呼应 R1 第 5 条）。
- 交互细节：额度接近耗尽（建议阈值 10 分钟）时 L1 先转 amber 预警，让用户**在耗尽前**就有决策机会；耗尽瞬间不做弹窗（会打断转写），走 L1/L2/L3 三层。

**Q2 / Q4 简述**：Q2（未登录）从界面看应走"联网卡需登录 + 详情层体验项置灰并给 `[去登录]` CTA"，与 R2 第 3 条同构，不建议硬中断；Q4（计量口径）是后端计费问题，但界面**已有暗示**——详情层按能力分行，若维持统一分钟数，就必须在两条能力卡的账单行写清"共用同一额度池"，否则界面结构会误导用户以为是两份额度。
