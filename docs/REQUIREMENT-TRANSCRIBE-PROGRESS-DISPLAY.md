# 需求记录：长音频转写进度可视化

## 1. Problem（要解决什么）

用户使用本地引擎（paraformer-v2 + qwen3:8b）处理长音频（实测案例：99 分 47 秒录音）时，原文页长时间只显示静态文案「原文整理中...」+ 转圈动画，没有任何进度、阶段或预计耗时信息。用户无法区分「正在正常处理」和「卡死了」，产生焦虑并倾向反复刷新、重复提交甚至判定产品不可用。

**根因（已核实，非猜测）**：

1. **前端浪费了既有信号**：后端流水线自带 `PipelineProgress(stage, message, percent)` 回调（`core/pipeline.py:54-63`），轮询接口 `GET /api/tasks/{task_id}` 的 payload 已包含 `progress`/`message` 字段（`app/routers/tasks.py:164-203`），前端类型也已声明（`frontend/src/api/types.ts:72-73`）——但**没有任何组件渲染它们**。`TranscriptPanel.vue:66-67` 的加载态只是一个静态 spinner。
2. **ASR 阶段进度信号本身是断档的**：本地 ASR 为单次全量批处理（`core/transcribe.py:295-370`、`core/engine_worker.py:210-262`），进度百分比从 45% 直接跳到 70%，中间对 100 分钟音频可能是数分钟到十几分钟的**零事件静默区**——即使前端渲染了百分比，也会在这里「卡住不动」。
3. **进度只写内存**：`on_progress` 回调仅更新内存 dict（`core/pipeline_runner.py:215-218`），不持久化；`message` 是调试语（如「提交转写任务...」），不是用户语言。

**证据来源**：2026-09-24 用户反馈截图（99:47 录音，页面停留在「原文整理中...」，状态栏「处理中/就绪」）+ 代码调研（本报告 §1 行号均为调研确认）。

## 2. Target Users and Scenarios

| 用户 | 场景 | 现在 | 交付后 |
|---|---|---|---|
| 本地引擎用户（隐私敏感/内网/断网） | 上传或录完 30–120 分钟长音频后等待出稿 | 只看到转圈，不知道进行到哪、还要多久，怀疑卡死 | 明确的阶段列表 + 实时百分比 + 预计剩余时间，知道「没卡死、还剩多少」 |
| 同上 | 等待期间决定去留 | 不敢离开页面，守在原地 | 明确告知「可离开/可最小化，完成后提醒」，用户安心去做别的事 |
| 云端引擎用户 | 同样等待（云 ASR 排队 + LLM 整理） | 同样只有静态文案 | 同一套进度 UI 自然受益（云路径阶段更快，多数时间只用到「阶段+百分比」） |

## 3. 产品目标与成功标准

**目标**：处理中的每一刻，用户都能回答三个问题——「在进行到哪一步」「还要等多久（或至少：有没有在动）」「我能不能离开」。

**成功标准（无正式 analytics 体系，采用可测代理指标）**：

- 处理全程中，UI 上可见状态（进度条/文案/计时任一）**最长静默间隔 ≤ 15 秒**（100 分钟本地音频实测）。
- 处理失败或超时时，用户能看到失败阶段与重试/回退入口（不依赖状态栏「就绪」误导——关联已修复的 DEF-FE-05）。
- 主观验证：5 分钟以上等待场景中，用户不再需要「刷新页面确认没卡死」的自助动作（可在 dogfooding 中口头验证）。

## 4. Scope（范围）

方案按投入产出分三期，**P0 单独即可解决约 70% 的焦虑问题**（因为主要矛盾是「有信号不展示」而非「没有信号」）：

### P0 — 前端渲染既有进度信号（本需求核心，必须交付）

- 将「原文整理中...」静态 spinner 升级为**进度面板**（原文/纪要/章节三处加载态统一）：
  - **阶段步骤条（4 步精简版，项目方 2026-09-24 裁决）**：`语音转写 → 原文整理 → 生成纪要 → 完成`。后端更细的阶段归并映射：音频归一化、热词处理归入「语音转写」；说话人分离、声纹匹配归入「原文整理」；标题、章节划分归入「生成纪要」。当前步高亮，已完成打勾；映射依据后端既有 stage/percent 区间（`core/pipeline.py:106-171, 225-300`）。
  - **百分比进度条**：渲染 `task.progress`，要求**单调不回退**；数字变化用缓动（3 秒轮询 → 平滑过渡），避免跳变观感。
  - **已用时长 + 预计剩余**：已用时长始终显示；ETA 在当前阶段进度推进 ≥10% 后按线性外推显示，格式保守（「预计还需约 6 分钟」，取整到分钟；无法估算时显示「本地引擎处理中，长音频需要更多时间」而非假数字）。
  - **安心文案与完成提醒**：「可以放心离开本页或最小化窗口，处理完成后会提醒你」；处理完成后给出**站内提醒**（会议列表角标 + 应用内 toast，点击直达该会议）。~~系统通知~~：Q5 实证 pywebview 6.2.1 壳内 Web Notification 恒 denied、无内建通知 API，**系统通知转 P1**（前端已预留零改动接入桥 `desktopNotify.ts`，待壳层/桌面端通知方案落地后接入，见 §11 Q5 裁决）。
- `message` 字段**不直接透传**给用户（当前为调试语）；前端按阶段查 i18n 文案表渲染用户语言。

### P1 — 补齐 ASR 阶段进度断档（消除 45%→70% 静默区）

- 本地 ASR 由单次全量推理改为**按音频分块循环推理、逐块上报**（45%–70% 区间内按已处理音频秒数/总时长线性推进）。可行性依据：FunASR 内部本就按 `batch_size_s=300` 分块（`core/engine_worker.py:229`）且返回逐句 `sentence_info`；实时链路已有分段计数上报的成熟模式（`core/realtime_local_asr.py:112, 256-267`）。
- 兜底要求：即使分块改造延期，ASR 静默区内也必须有**心跳**——轮询 payload 中该阶段的已用秒数持续增长，配合 P0 的「已用时长」展示即可证明「在动」。
- `on_progress` 顺带持久化任务状态（当前仅内存，`core/pipeline_runner.py:215-218`），保证刷新页面后进度可恢复。
- **系统通知回归（Q5 降级承接）**：选定桌面壳通知方案（pywebview 原生桥或替代通道）后，经 `desktopNotify.ts` 接入桥零改动启用系统通知（标题含会议名、点击直达会议页、未授权降级不索权）。

### P2 — 结果增量可见（把「等待」变成「提前看」）

- ASR 分块完成后，**已转写段落即时进入原文 Tab**（转写部分先可见、后定稿），复用 REQ-LOCAL-REALTIME-INCR 的分段上屏机制，不重复建设。
- 纪要生成（qwen3:8b）改流式输出（管线内现为同步非流式 `chat_completion`，`core/llm.py:275`；流式函数 `chat_completion_stream` 已存在，`core/llm.py:510`），纪要 Tab 打字机式呈现。

### Non-Goals（本期明确不做）

- 不承诺**逐字级**会中流式识别（沿用 PRD-LOCAL-ENGINE 既有非目标；P2 的「增量」是会后段级，不是会中字级）。
- 不把轮询改造为 SSE/WebSocket（3 秒轮询 + P0 前端缓动 + P1 心跳已满足 ≤15s 静默指标；joblog 暴露端点属工程优化，不列为本需求验收项）。
- 不做真实「剩余时间」机器学习预测，ETA 仅用线性外推，估算不出来就不显示。
- 不改变任何转写/纪要算法与质量。

## 5. User Flow

1. 用户结束录音或上传音频 → 进入会议页，顶部「处理中」徽标保留。
2. 原文 Tab 显示进度面板：步骤条定位「语音转写」，进度条 45%，「已用 2 分 10 秒 · 预计还需约 8 分钟」，下方安心文案。
3. 用户可自由切换 Tab、离开本页、最小化窗口；任务后台继续。
4. 阶段推进时步骤条逐项打勾；P1 交付后转写阶段百分比连续流动。
5. 完成 → 进度面板替换为正文，同时给出站内角标与应用内 toast（点击直达该会议）。
6. **失败路径**：任一阶段失败 → 面板停留在失败阶段并标红，显示「转写失败（已处理至 62%）」+「重试」按钮；云端可回退时（`can_fallback_cloud`）提供「改用云端引擎重试」次按钮。
7. **恢复路径**：处理中刷新页面/重开应用 → 重新轮询后进度面板按最新 task 状态重建（依赖 P1 持久化；P0 期间至少显示阶段与已用时长的合理近似）。

## 6. Functional Requirements（用户故事）

### R1：进度面板替代静态 spinner（P0）
- 场景：本地引擎处理 100 分钟音频，进入会议页。
- 行为：渲染步骤条 + 百分比 + 已用时长，数据源为 `GET /api/tasks/{id}` 的 `progress` 与阶段映射；进度只增不减；文案走 i18n（zh-CN / en-US 同步）。
- 验收：见 §7 AC-1/AC-2/AC-3。
- 优先级：P0。

### R2：ETA、安心文案与完成提醒（P0）
- 行为：阶段内进度推进 ≥10% 后显示线性外推 ETA（分钟取整）；估算不成立时显示无数字的安抚文案；面板固定显示「可离开本页，完成后提醒」。任务完成后推送站内角标（会议列表）+ 应用内 toast（含会议名，点击直达会议页并清角标）；用户正停留该会议页时不弹 toast，仅更新页面。系统通知按 Q5 实证降级转 P1（见 §11），P0 前端保留零改动接入桥。
- 边界：进度长期停滞（>60s 无变化且无心跳）→ 文案切换为「本地引擎正在处理长音频，仍在进行中」，不显示失败。
- 优先级：P0。

### R3：ASR 分块进度上报 + 心跳（P1）
- 行为：本地 ASR 按块推理，`progress` 在 45–70 区间按已处理音频时长线性推进，单块间隔 ≤60s；`on_progress` 写入持久化任务存储。
- 边界：分块失败仅重试该块，不使整任务回退百分比。
- 优先级：P1。

### R4：失败与回退呈现（P0 简化版 / P1 完整版）
- 行为：失败时面板标红停留阶段，提供重试；`can_fallback_cloud=true` 时提供云端回退入口（复用既有状态字段）。
- 优先级：R4-简（失败文案+重试）P0；R4-全（回退入口联动）P1。

### R5：结果增量可见（P2）
- 行为：已转写分段即时出现在原文 Tab（带「转写中」分隔线，与定稿区分）；纪要流式呈现。
- 依赖：REQ-LOCAL-REALTIME-INCR 的分段机制、`chat_completion_stream` 接入管线。
- 优先级：P2。

## 7. Acceptance Criteria（QA 可直接执行）

- **AC-1（happy path）**：本地引擎处理 ≥60 分钟音频，从提交到完成全程观察 UI：任意时刻进度面板可见阶段与百分比；除「说话人分离」等已知短阶段外，UI 可见状态最长静默 ≤15s（P1 前允许 ASR 区间靠「已用时长」跳动满足）。
- **AC-2（单调性）**：轮询采样 30 次，`progress` 渲染值不回退；轮询延迟期间数值以缓动过渡，无倒退动画。
- **AC-3（语言）**：面板不出现后端调试语（如「提交转写任务...」）；zh-CN 与 en-US 下文案完整。
- **AC-4（失败路径）**：模拟 ASR 阶段失败（断开引擎服务），面板显示失败阶段标红 + 重试按钮；重试后进度从合理位置重新推进。
- **AC-5（离开与恢复）**：处理中切换至其他会议再返回，进度面板仍反映当前任务真实阶段；刷新页面后面板重建且无「假 100%」。
- **AC-6（云端回归）**：云引擎短音频（<10 分钟）处理时同一面板正常展示，各阶段快速流转，无卡帧或残留 spinner 双态叠加。
- **AC-7（P1 专项）**：本地 ASR 期间连续观察 5 分钟，百分比至少推进 2 次；`progress` 变化持久化（重启应用后 task 记录含最后进度）。
- **AC-8（完成提醒，v0.3.0 按 Q5 修订）**：后台处理完成时（应用最小化或停留在其他页），出现应用内 toast（含会议名）与会议列表角标，点击直达对应会议页并清角标；用户正停留该会议页时不弹 toast、不重复提醒；角标状态持久化（重启应用后未读角标不丢失、已读不残留）。
- **AC-9（步骤条归并）**：观察全程步骤条仅出现 4 步（语音转写/原文整理/生成纪要/完成），归一化、说话人分离、标题章节等中间处理不单独成步，但当前步定位与后端阶段区间映射一致（QA 可对照 task 日志核验）。

## 8. Data and Permission Requirements

- 无新增用户数据、无隐私面变化（全部为本机已有任务状态字段的展示）。
- 字段依赖：`status/progress/message/failed_stage/can_fallback_cloud`（均已存在）；P1 新增 `stage_started_at`（或等价心跳时间戳）供「已用时长」精确计算。

## 9. Risks

| 风险 | 等级 | 缓解 |
|---|---|---|
| 后端百分比区间与实际耗时严重不成比例（如 ASR 占 90% 时间但只占 25% 区间），进度条「看着假」 | 中 | P1 按音频秒数线性化 ASR 区间；P0 阶段按耗时权重调整映射表（工程实现时用实测 RTF 校准，不硬编码） |
| ETA 线性外推在 LLM 阶段不准，承诺「还需 2 分钟」结果 8 分钟，反噬信任 | 中 | ETA 只在有阶段内进度样本时显示、取整、措辞用「约」；宁可不显示也不显示错的 |
| 分块 ASR 改造影响转写质量（跨块上下文、标点后处理） | 中 | P1 独立验收：分块前后同音频 diff 抽查；句子边界合并规则先行设计评审 |
| 三处加载态（原文/纪要/章节）+ 顶部徽标 + 状态栏多源状态不一致（DEF-FE-05 同类问题） | 低 | R1 统一由单一进度组件消费同一 task 数据源，禁止各面板自判状态 |
