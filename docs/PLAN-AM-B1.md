# Plan: 让后端以 access_mode 为唯一路由判定入口，用户计费归属与数据去向在升级后保持可感知、可回滚

**Complexity:** Medium — 新增用户侧字段与一次性迁移 + 新路由解析模块 + 新查询端点，跨 4 个消费方文件。

## Goal

Enable 设置/转写/纪要链路以单一 `access_mode` 判定「花谁的钱、数据去哪」so that 路由不再被 engine.mode+prefer_subscription 双头读取，且任何跨模式变化可被前端查询（供 AM-F1 toast）。

## Deliverables

- 数据字段: `settings.json` 新增 `access_mode ∈ {local,hosted,byok} | null`、`expert_mode: bool`、迁移标记 `_access_mode_migrated: bool` → 承载三卡片统一心智（T1）
- 函数: `app/settings_store.py` — `derive_access_mode()`（§4 映射纯函数）、`derive_expert_mode()`、`migrate_access_mode()`（一次性迁移，旧字段原样保留）、`get_access_mode()`（持久值优先，未迁移时惰性推导）、`get_expert_mode()`、`set_access_mode()`/`set_expert_mode()`（写路径同步旧字段 engine.mode/asr.mode 保回滚）→ 迁移与读写收口在数据层
- 模块: `core/routing.py` — `get_routing_decision() -> {configured_access_mode, effective_mode, route, route_override, reason, quota}`；唯一读取 access_mode(+prefer_subscription 覆盖仅作用于 byok→hosted 的 D2 显性变化) 的解析器 → T2 收敛双头读取
- API 端点: `GET /api/settings/routing`（前端查询当前路由结论与 override 事件，供 AM-F1 toast）；`GET /api/settings` 响应新增 `access_mode`/`expert_mode`；`POST /api/settings` 接受并校验 `access_mode`/`expert_mode` → 状态可感知面
- 行为改造: `core/llm.py::_should_use_cloud`、`core/transcribe.py::_get_asr_mode` 改为消费 `get_routing_decision()`，删除各自对 engine.mode / prefer_subscription 组合的独立读取 → AC-T2①
- 契约文档: `docs/API_CONTRACTS.md` §13 接入方式路由契约（字段、映射表、端点、计费三路径与 metering 口径对齐说明）→ AM-F1 派工依据
- 测试: `tests/test_access_mode_migration.py`（§4 全组合 + expert_mode 推导 + 读写兼容）、`tests/test_routing_decision.py`（local/hosted/byok × prefer_subscription × quota/cloud_enabled 矩阵）

**Out of scope:** frontend/ 全部文件（AM-F1）；core/pipeline.py（DC-DEC-B1 在途）；decisions 相关；不新增计费规则；不改 users 登录体系。

## Acceptance Criteria

AC-1  [Happy]     Given 存量 settings.json 含 §4 五种组合之一，When 执行迁移，Then access_mode 按映射表落值（local/proxy→local/hosted；direct+ps=false→byok；direct+ps=true→hosted；未配置→null），旧字段逐字节保留，且 `_access_mode_migrated=true` 后再次迁移不改变已持久值。
AC-2  [Happy]     Given 存量配置含自定义 base_url/model 覆盖或非默认 Key 组合，When 迁移/读取，Then expert_mode=true；标准配置则 false。
AC-3  [Compat]    Given 旧版本前端只写旧字段（engine.mode 等），When 读写一个兼容窗口内执行，Then 旧字段仍可读取生效，写 access_mode 同步产生旧字段值（回滚后行为可用）。
AC-4  [Routing]   Given access_mode=local/hosted/byok 分别配置，When 判定路由，Then route 依次为 local/cloud/direct 方向；`_should_use_cloud` 仅在 route=cloud 时为 True；local 不触发 record_usage（与 metering.is_metered 口径一致）、hosted 走配额、byok 走自有 Key。
AC-5  [D2 覆盖]   Given access_mode=byok 且登录用户 prefer_subscription=true 且 quota>0 且云端可用，When 判定，Then route=cloud 且 route_override=true、reason="prefer_subscription"，可经 GET /api/settings/routing 查询；quota=0 或云端不可用时回落 route=direct（不误扣）。
AC-6  [Edge]      Given access_mode=null（未配置/新装），When 判定，Then 走与现状等价的 legacy 兜底（_should_use_cloud 原逻辑），不强制改变未引导用户的行为，且 GET /api/settings 返回 access_mode=null 触发引导。
AC-7  [grep]      路由判定收敛后，`_should_use_cloud`/`_get_asr_mode` 源码中不再出现对 `engine.mode`+`prefer_subscription` 组合的独立读取（判定逻辑仅存在于 core/routing.py）。

## Assumptions（无追问裁决）

- A-i1: `engine.mode=cloud`（桌面端旧默认）迁移归 hosted——与 proxy 同为云代理计费路径，A1 裁决同理延伸；测试覆盖。
- A-i2: 惰性推导不写盘；仅显式迁移（启动/POST）持久化，避免 GET 副作用。
- A-i3: prefer_subscription 覆盖仅作用于 byok（direct 语义等价），hosted 用户本就走云代理无需 override；与迁移映射 A1 一致。
- A-i4: expert_mode 触发口径：llm/asr 的 base_url 或 model 与默认值不同、voiceprint.cloud 配置非空、旧版 flat api_key 存在，任一命中即 true。
- A-i5: API_CONTRACTS.md 追加为 §13，避开在途 DC-DEC-B1 的 §12（同文件尾追加，合并时顺序冲突可解，已在回报中登记协调）。

## Implementation Path

1. 数据层：settings_store 新增字段读写 + derive/migrate 纯函数（解锁 T2 与 API）
2. 路由解析：core/routing.get_routing_decision（唯一入口，含 null 兜底）
3. 消费方收敛：llm._should_use_cloud / transcribe._get_asr_mode 改接解析器
4. API：GET/POST /api/settings 扩展 + GET /api/settings/routing
5. 测试：§4 全组合迁移矩阵 + 路由矩阵 + 兼容读写（pytest）
6. 文档：API_CONTRACTS.md §13；grep 级验证证据
