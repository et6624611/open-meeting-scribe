# 需求记录：本地引擎分段增量上屏

## 1. Problem（要解决什么）

当前本地引擎在**录音期间完全不产出转写文字**：`core/realtime_asr.py:222-233` 在 `engine.mode=local` 时直接抛 `realtime_degraded_to_batch`，转写全部推迟到录音结束后一次性全量批处理（`core/transcribe.py:321` → 单请求上限 `ENGINE_REQUEST_TIMEOUT=180s`）。

由此产生三重损失：

1. **会中不可用**：主持人无法在会中看到转写内容，录音页退化为「只有计时器的录音机」。云模式同期提供句级实时预览（`record.py:332-334` 双喂 `transcriber` + `diarizer`），形成明确的能力落差，且**只有本地用户承受**——这与「本地是可选引擎而非降级引擎」的定位冲突。
2. **长会议直接失败**：30 分钟以上会议触碰 180s 单请求上限即 `engine_timeout`，本地模式 `can_fallback_cloud=False` → 整场转写丢失、录音白录（详见 WP-H 第 1 项）。
3. **口径不可信**：录音页横幅写「按分段批处理输出」（`RecTranscriptPanel.vue:65`、`zh-CN/recording.json:31`），与实现不符；用户按文案期待分段，实际什么也等不到。

项目方 2026-09-24 裁决取**方案 B**：真正把分段增量上屏做出来，而非把文案改回「结束后一次性转写」。

## 2. Target Users and Scenarios

| 用户 | 场景 | 现在 | B 交付后 |
|---|---|---|---|
| 隐私敏感的主持人（法务/医疗/政企内网） | 会中回看刚才说了什么、确认没漏人发言 | 全程无文字，只能等散会 | 分段级近实时可见 |
| 断网出差/内网部署用户 | 会中即时校对专有名词（热词映射已生效） | 无法即时发现识别错误，纪要带错 | 段内即可发现并会后修正 |
| 长会议用户（≥30 分钟） | 大会/评审会完整出稿 | 大概率超时失败 | 分段自然规避单请求上限 |

**非目标用户**：期望逐字级流式（说一个字上一个字）的用户——该体验在本地引擎**仍属非目标**（CPU 上 funasr 非流式模型做不到，且 PRD 现有非目标判断仍成立）。本需求只把「分段」从承诺变成事实。

## 3. 边界：本需求 vs PRD 现有非目标

`docs/PRD-LOCAL-ENGINE.md:72` 现文本把两件事捆在一起，需拆开：

- 「逐字级流式识别」→ **保持非目标**（不动）。
- 「实时链路降级为分段批处理」→ **升格为 In Scope**（新 R9），原文需改写为「本地模式提供分段增量上屏（段级近实时），不承诺逐字级流式」。

实时聚类的 MFCC 本地降级、不为实时侧恢复 torch 两项约束**保留不变**。

## 4. 功能定义与可测目标

**行为**：录音进行中，引擎按语音段闭合（建议 VAD 静音驱动 + 最长时长兜底，段长量级 20–60s，待 D-I3 实测定）将音频切片送本机 FunASR 推理，段结果定稿后经既有 `push_realtime_msg` 以 `sentence` 事件上屏；无 `partial` 事件（逐字非目标）。

**感知延迟目标（P95，待设计/项目方确认档位）**：

| 指标 | 建议门槛 | 依据 |
|---|---|---|
| 段闭合 → 该段上屏 | P50 ≤ 8s，P95 ≤ 20s | Spike RTF≈0.081 → 60s 段推理 ≈ 5s，余量给排队与标点 |
| 录音音频完整性 | 30 分钟会话音频时长偏差 < 1s | 采集不得被推理挤掉帧 |
| 引擎常驻期间失败恢复 | 单段失败不导致整场预览中断 | 见 D-I1 |

**定稿一致性**：会中上屏内容即会后定稿内容（方案 B 建议，见 D-I2）——禁止「结束后重跑全量导致用户看到的文字整体变化」。

## 5. 技术前提与已识别风险（工程必须先认，再排期）

1. **引擎请求是全局锁串行的**：`core/engine_host.py:174-201` 单条 JSON Lines 请求 + `self._lock` + 同步等待。分段推理会与声纹 embedding 请求（R3 本地 `LocalCamPlusProvider`，`core/embedding_provider.py:431-453`）争用同一把锁 → 会中可能出现互相排队、延迟叠加。
2. **超时被判为引擎不健康**：同处注释明确「超时 ⇒ unhealthy」，调用方 stop/重启（`engine_host.py:259`）。任一卡住的段会连带**重启常驻引擎**，重付冻结态 86s 冷启动（Spike §3.2）→ 需要「单请求失败 ≠ 引擎不健康」的语义修订（D-I1）。
3. **段间 speaker 编号不可对应**：FunASR 每次 `generate` 独立返回 `spk` 局部编号（`core/engine_worker.py:148-156`），跨段不成立。**说话人身份唯一事实源应改用既有增量聚类**：`core/diarization_cluster.py`（`feed_audio` / `get_speaker(begin,end)`、192 维阈值自适应、持久 speaker profile），云侧实时链路已是这一套（`record.py:332-334`）。这条同时把「最终全量重跑 vs 增量结果」的身份漂移问题消掉。
4. **段边界与标点**：`ct-punc` 为可选项（`core/model_registry.py:46` 附近，D-R1 决策：唯一可裁剪大件）。段切在句中时缺标点模型会出粘连文本，需边界合并规则 + 无标点档下的可读性实测（与 ROADMAP「真机验收 ct-punc 降级先实测后议」并项，勿重复决策）。
5. **热词映射须逐段应用**：R2 把转写后替换定为必配项（`core/transcribe.py:264-295`），增量路径同样必须过 `_apply_local_hotword_mappings`，否则会中看到的文本与定稿不一致。
6. **内存**：10 分钟全量峰值 RSS 3.3GB（Spike §2.2）。分段单次应更低，但增量聚类音频缓冲 + 累积结果需在 30/60 分钟会话下实测，AC-3 门槛（16GB 机型 ≤8GB）不因本需求放松。
7. **前置依赖 D-G1**：分段增量要跑在**冻结包**里，而当前主包 `excludes=['torch','torchaudio']`（`build/pyinstaller.spec:103`）——引擎包形态未定前，本需求只能在 venv 里开发验证，真机交付无路径。

## 6. 决策点裁决结果

> **授权性质（诚实标注）**：项目方 2026-09-24 给出 blanket 授权「我没答复的都按你给出的建议执行」，并于同轮明确「包括指派工程师」（本包 owner = 后端工程师 `a4cdbd0ca795`）。以下 D-I1~D-I4 为**产品经理按建议值代理裁决**，不是项目方逐项亲口拍板；任一项被推翻只需回退本记录 + PRD 对应条目。实施中若发现建议值技术上不可行，**必须回报而非静默变通**。

- **D-I1｜引擎故障域划分 → 采纳「单段失败只丢该段、不重启常驻引擎」**。工程前提：把 `core/engine_host.py:174-201` 的「超时 ⇒ unhealthy」拆成 `request`（可失败）与 `health`（进程级）两级语义；若子进程内异常确实无法隔离（如同进程 OOM），退回「连续 N 段失败才重启」的可配置策略，N 由实测定。**不可行即回报，不要自行降级方案。**
- **D-I2｜定稿策略 → 采纳「增量段拼接即定稿」，结束后不重跑全量**。连带效果（已知并接受）：长会议 `ENGINE_REQUEST_TIMEOUT=180s` 整场失败问题在**实时链路**自然消解；WP-H 第 1 项范围收窄至「导入音频 / 非实时任务的长文件路径」，**仍须独立修，不因本条关闭**。
- **D-I3｜段长与闭合策略 → 不在本记录定数值**。要求：实现为 VAD 静音驱动 + 最长时长兜底且**可配置**，真机各跑一场 20s 档与 60s 档、带上屏延迟分布回来定默认值。禁止拍脑袋写死常量。
- **D-I4｜优先级 → 采纳 P1，不阻塞 v10 AC-1 断网闭环发布**。理由：「数据永不出设备」的核心主张现状已成立（录音+转写+声纹+纪要+导出全本地），本需求属会中体验升级。若改判 P0，v10 里程碑与验收排期需同步重排，且强依赖 D-G1 先落地。
- **补充裁决｜空窗期文案 → 已执行**：按 §8 两步走建议，录音页横幅中英文案已收敛为如实描述（不再宣称"分段批处理输出"），WP-I 验收通过的同一版本再切增量口径。i18n key `recording.transcript.local_batch_notice` **未改名**（避免牵动组件与测试），仅改值。

## 7. Acceptance Criteria（草案）

1. 本地模式录音页在 ≥3 段不同长度（10/30/60 分钟）真机会议中均出现分段文字，且**最后一段上屏延迟 P95 ≤ 20s**。
2. 全程抓包零出网（对齐 AC-1 白名单，仅 localhost）。
3. 同一说话人在整场会议中编号不跳变；声纹姓名化结果与现有云/本地注册表一致（对齐 AC-6）。
4. 会中上屏文本 = 会后定稿文本（除 D-I2 明确选 A/C 外）；热词映射在会中即生效。
5. 30 分钟与 60 分钟会议均完整出稿，不出现 `engine_timeout` 导致的整场失败。
6. 单段失败时给「本段暂缺，已继续」级提示，不出现 `type:"error"` 红色报错刷屏（并入 WP-H 第 2 项口径）。
7. AC-3 内存门槛复测通过；云模式路径（proxy/direct/cloud）行为与包体零变化（AC-7）。
