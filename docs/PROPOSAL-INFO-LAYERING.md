# PROPOSAL-INFO-LAYERING：AI 输出信息的三层文本结构

> 状态：**v0.2.0 提案——①②③ 期已实施并验证（2026-09-29）**。① 提示词契约（`summary-template.md` v1.3.0 + `SYSTEM_PROMPT` + 两角色 `insights.md` v2.1.0 + 预算块注释豁免声明）；② 洞察 `note` 字段全链路贯通（core 解析/落盘/前端渲染/chat与CLI注入）；③ 洞察卡用色收敛（装饰全中性化，`--proactive` 仅留域标识+未读小圆点+主按钮）。回归 75 passed、Ruff 干净、vue-tsc 零错、前端已构建、后端已重启并实测 `note` 字段返回。三个开放项（§9）按提案倾向执行：首期不剥离、纯文本、暂不启用左紫条；④ 观察期待真实会议反馈。
> 借鉴来源：汇报演示页的三层信息结构（标题=树干、正文=枝、虚线分隔小字注解=备查明细）。**借的是文本按认知深度分层写作的内容结构，不是"小字灰色+虚线"的视觉样式**——样式只是分层的最后一步呈现。

---

## 1. 背景与动机

### 1.1 问题：信息焦虑的根源不是信息多

用户面对 AI 输出（纪要、洞察）时的焦虑，来自**无法在打开信息的瞬间判断"这条值不值得我读完"**：想略读找不到抓手（没有独立成立的结论行），想深读发现明细也不在（依据、构成、例外被模型丢弃或混写在正文里）。焦虑的本质是"层与层之间的断层"。

三层递进结构把"阅读深度"的选择权还给用户，两个承诺各自独立成立：

| 层 | 角色 | 承诺 |
|---|---|---|
| 标题 | 结论 / 树干 | 只看这一行，就知道"这是什么、结论是什么" |
| 正文 | 支撑 / 枝 | 标题的完整句表述，10 秒读完，本身自洽 |
| 注释 | 明细 / 备查 | 事实依据、构成清单、例外说明——不读不影响理解，读了能回答追问 |

**退，不构成信息缺失；进，不构成认知扑空。**

### 1.2 这是写作规范，不是 UI 规范

样式只是"把同一段文字渲染成三种字号"，那什么都不过滤。真正的分层要求 AI 在生成时就把内容拆开——同一层内不得混写结论和明细。因此本方案的落点在**提示词模板与输出契约**（`summary-template.md`、`core/insights.py` 提示词、`build_page_budget_block` 链路），前端只是把已有的层忠实渲染出来。

已有的相邻实践（说明方向已被验证过，但当时是交互层分层，文本层分层是其前提）：

- 决策流面板方案 A：折叠态 3 元素 / 展开态 why·how·outcome——如果正文没按层写，折叠/展开只是把一坨文字藏起来；
- 洞察板设计三原则（Board Spec v0.2）：图主导、文本 cell 降级为折叠详情层；
- 一页纸系数：管"量"（数量预算），本方案管"形"（单个信息块的内部结构），二者正交互补。

### 1.3 现状审计：分层基线在哪

| 战场 | 现有层次 | 缺口 |
|---|---|---|
| 纪要·主要结论/决策 | `**短标题**：完整内容` 两要素写法（`core/summarize.py` `split_decision_title`，DC-R2-b D5 已支持拆层） | **无注释层**——依据、明细、例外要么挤进正文，要么丢失 |
| 纪要·议题归类 | `### 议题：标题` + 1-2 句总结 | 总结与明细混写，无逃生通道 |
| 洞察卡 | `title`（折叠层）→ 图 → `body` 图注 → `solution` 行动建议 | **无备查层**——`[待确认]` 的 ASR 异写、依据出处散落在 body 里 |
| 决策流节点 | 折叠态 3 元素 / 展开态 why·how·outcome | 交互分层已验证，文本层跟随即可，**本次不动** |

结论：改造不是从零建层，而是**补齐缺失的第三层（注释），并把"分层写作"从隐性惯例升格为显式契约**。

## 2. 三层文本契约（核心定义）

每个信息块 = **标题（结论）→ 正文（支撑）→ 注释（备查）**。

### 2.1 注释层的内容资格规则

只有能回答以下三类追问的素材才有资格入注：

1. **依据是什么**：谁在什么时间说的（说话人 + 转写时间戳，如「说话人2 07:34」）；
2. **具体是哪些**：构成清单、覆盖范围、数量明细；
3. **有什么例外**：`[待确认]` 的异写变体、未敲定点、适用边界。

### 2.2 明确禁止入注（防止注释层变成垃圾桶）

- ❌ 置信度分数、token 用量、内部字段名等工程元数据；
- ❌ 需求编号类技术琐碎（借鉴来源中该层是刻意脱敏的——保留的是"被追问时最可能被问到的事实"）；
- ❌ 与正文重复的转述（注释必须携带正文没有的增量信息）。

若注释层混入噪声，用户偶尔瞄一眼时看到的是垃圾，"退可略"的承诺即被违背。

### 2.3 体量约束

- 纪要清单条目内联注：≤40 字，至多一个；
- 纪要议题引用块注：≤40 字，至多一行；
- 洞察卡 `note`：≤60 字，可选字段。

## 3. 纪要侧改造

### 3.1 清单条目（主要结论/决策）：注释内联于同一行

**解析器硬约束决定写法**：`parse_decisions_with_status`（`core/summarize.py` L548-）逐行扫描章节正文，任何独立附加行都会被 `_BULLET_PREFIX_RE` 宽容采集成一个假决策节点（引用块 `>`、普通行均不豁免）。因此清单条目的注释**必须与条目同行**：

```markdown
1. **差旅报销口径统一**：所有超标单据改由部门负责人事前审批（注：说话人2 07:34 提出，另有"圣一/新PMS"两种写法待确认）
2. **……**：……
```

兼容性分析（**零解析器改动**）：

- `_DECISION_TITLE_RE`（`^\*\*...\*\*[：:]`）不匹配括号内容，`split_decision_title` 天然把 `（注：…）` 归入 content；
- `[待确认]` 前缀、跨章节查重、`how` 字段落盘逻辑均不受影响。

代价：注释随 content 落入决策流节点的 `text` 字段。可接受——决策流展开态本来就该能回答追问；是否剥离到独立字段见 §9 开放项 1。

### 3.2 议题块：注释用 Markdown 引用块（独立行，安全）

议题归类不走决策解析器，可用独立行分层：

```markdown
### 议题3：数据源切换
讨论倾向在 Q4 前把费控报表迁至新数据平台，旧平台并行保留一个季度。
> 依据：说话人3（22:10）；涉及报表约 12 张；切换窗口未敲定[待确认]
```

`>` 引用块在纪要 Markdown 渲染中天然呈现为次要层，前端零改动。

`> ` 同时定义为全局注释层的 Markdown 语法。若未来清单侧也需要独立行注释（放宽 §3.1 的同行约束），只需在解析器行扫描处加一个 `>` 开头跳过的守卫——5 行级改动，含单测。

### 3.3 模板与回退常量同步

| 文件 | 改动 |
|---|---|
| `data/agent/_roles/_builtin/meeting-minutes/summary-template.md` | version 1.2.0 → 1.3.0；核心原则新增第 6 条「三层写作」（含 §2.1 资格规则与 §2.3 体量约束）；输出结构的"主要结论/决策"格式硬约束补条目示例；"议题归类"补 `>` 注释行示例 |
| `core/summarize.py` `SYSTEM_PROMPT` | 与角色模板**同步修改**，防止双源分叉（此前已有分叉教训） |

## 4. 洞察卡侧改造

### 4.1 JSON 契约：新增 `note` 字段

```json
{
  "title": "一句话概括",
  "body": "图注（1-3 句话，画布格式时附「阶段名：一句话」描述）",
  "solution": "行动建议（可选）",
  "note": "备查明细（≤60字，可选）",
  "has_finding": true,
  "diagram": "Mermaid 语法或空字符串"
}
```

三层映射与分工：

| 字段 | 层 | 定位（不变/新增） |
|---|---|---|
| `title` | 标题层 | 折叠层，承诺"看一眼就知道是什么"（不变） |
| `diagram` + `body` | 正文层 | 图主导 + 启发式提问图注（不变） |
| `note` | 注释层 | **新增**：依据出处、`[待确认]` 异写、构成清单、例外说明 |
| `solution` | 行动建议 | 保持不动（它是"下一步"，不是"备查"） |

body 中目前混写的备查信息（如 `[待确认，原文或作"圣一"]`、非阶段描述的出处引用）统一迁入 note。

改动位置：`core/insights.py` `INSIGHT_ANALYSIS_PROMPT` §返回 JSON 及正文小节（新增"### 备查注释（note 字段）"写作规则）。

### 4.2 后端解析与兼容

- 解析函数（L229 附近）：`"note": str(result.get("note") or "").strip()[:60]`，缺字段降级为空串——**旧卡无 note 完全兼容，无需存储迁移**；
- `_format_existing_insights`（只读累进的已有卡摘要）：条目改为 `- {title}：{body}` 后追加 note 摘要，防重复判断仍以 title 为主，不受影响；受 `EXISTING_INSIGHTS_MAX_CHARS=2000` 总预算约束，note 不计入 `EXISTING_INSIGHTS_BODY_CHARS=120` 的 body 截断，单独截 40。

### 4.3 前端渲染

| 位置 | 改动 |
|---|---|
| `frontend/src/views/recording/RecInsightsPanel.vue` | 展开态在 body（`.rec-insight-body-text`）之后、solution 之前渲染 note（`v-if="msg.note"`），沿用 solution 的"标签 + 文字"结构 |
| 样式（`ai-panel.css` 或 insights 所在模块 CSS） | note 层：`--fs-11` + `--subtle` + `border-top: 1px dashed var(--border)`；全部取自现有 token 标尺，禁止硬编码色值 |
| 折叠态 / deferred 降级列表 | 不动（deferred 整卡降折叠层与卡内分层正交） |

### 4.4 上下文注入通道（"追问不扑空"的第二保障）

页面注释层允许用户略过，但 AI 必须看得到——保证"页面上略过的，问 AI 时能补回来"：

| 位置 | 改动 |
|---|---|
| `core/chat_context.py` `build_insights_context_block` | 洞察摘要块携带 note（note 截断 60），计入现有 1200 字符总预算 |
| `core/cli_engine/context_export.py` `_render_insights` | CLI 引擎 `context/insights.md` 导出同步携带 note |

（两处维护是既有 ADR「AI 会话上下文注入会议洞察台摘要块」已接受的代价，本方案沿用。）

## 5. 与一页纸系数的关系：注释层不计入预算

**决策：`（注：…）` / `note` 内容不计入结论层字数预算（1页≈900字口径）。**

理由：预算的作用是逼迫"主张取舍"——超预算时裁过程性描述、裁低优先级条目；而注释层是"备查素材"，不占读者扫读认知。若计入预算，模型会为省额度把异写、出处、例外直接丢弃——恰恰重造"认知扑空"，与方案目的相悖。

落地：`core/summarize.py` `build_page_budget_block` 的说明文字追加一句「（注：…）注释层与洞察 note 不计入本预算，但须遵守内容资格规则」。

## 6. 用色克制：层次用排印承载，色彩只留状态

> 用户定调：洞察台当前使用了大量色彩，颜色的使用要克制。本节为评估结论与收敛规则，与三层文本契约同属本方案——**三层分层的呈现机制正是排印（`--fs-*` 字号阶梯 + `--fg/--muted/--subtle` 中性色阶 + 虚线分隔），色彩不应再承担层次表达**。

### 6.1 现状盘点：`--proactive` 紫色在洞察台的 13 处使用

（样式位置：`recording-view.css` L112-320 全局 + `RecInsightsPanel.vue` L315+ scoped）

| # | 用色点 | 现状 | 语义 |
|---|---|---|---|
| 1 | 面板头未读计数徽章 | `background: --proactive` 实心紫胶囊 | 状态（未读）✅ |
| 2 | 「观察中」按钮激活/加载态 | `color/--proactive-soft` 底 | 状态（功能开启）✅ |
| 3 | 扩展按钮激活态 | 同上 | 状态 ✅ |
| 4 | 卡片折叠头容器 | `--proactive-soft` 底 + `--proactive-mid` 四边描边 + **3px 左侧紫条** + hover 再加深 | 装饰（域标识）❌ |
| 5 | 未读卡外环 | `box-shadow: 0 0 0 1px --proactive-mid` | 状态（未读）⚠️ 与 #4 边框叠加冗余 |
| 6 | 类别徽章 `rec-insight-cat` | 紫字 + 紫底 | 装饰 ❌ |
| 7 | 卡片展开体容器 | 与 #4 同套紫色容器 | 装饰 ❌ |
| 8 | body 内 Markdown：h3 下划线、`li::marker` | 紫色 | 装饰 ❌ |
| 9 | solution 区块：label 紫字、`li::marker` 紫 | 紫色 | 装饰 ❌ |
| 10 | 行动按钮组：普通紫字紫边、**主按钮实心紫底** | 大面积紫 | 半状态（可操作）⚠️ |
| 11 | 图主输出态：`--proactive-mid` 描边 + 紫色投影 | 紫色晕影 | 装饰 ❌ |
| 12 | 画布：chip hover 紫边、时间戳紫字、legacy 图谱节点紫描边 | 点缀 | 半语义 ⚠️ |
| 13 | 下拉项 hover 紫字 | 紫色 | 装饰 ❌ |

**已有的正确先例**：`is-acknowledged` 态整卡降为中性色（注释原文即「切换为系统默认色系，**让出视觉空间**」）——这套逻辑已经承认紫色是视觉侵占，但只把它用在了"已确认"这一种状态上，默认态仍然是满屏紫。

### 6.2 诊断

1. **三重冗余编码**：一张普通未读卡同时以「紫底 + 紫描边 + 左紫条」（外加未读紫环 = 四重）表达同一个"这是洞察"的语义——违背方案 A 已确立的"单一编码"原则（颜色承担扫读信号时，其余通道不应重复说话）；
2. **色彩语义通胀**：紫色同时表示"域归属、未读、可操作、层级强调"四种语义，读到第三张卡时颜色已不传递任何增量信息，只剩噪声——这正是"大量色彩"造成焦虑的机制；
3. **与既有视觉语言规范冲突**：「背景分区 + 分割线」规范明确要求移除四边边框卡片容器、用 `--bg/--surface/--surface-2` 亮度阶梯分区、状态指示优先轻量元素——洞察卡是全仓对该规范偏离最重的区域；
4. **与主题系统原则冲突**：主题卡记载"品牌标识用中性对比色，accent 仅用于交互反馈"——同理，域标识色也应仅用于交互与状态反馈，不应用于静态装饰。

### 6.3 收敛规则

**R1 色彩只做两件事：域归属一处、状态信号两处。**

| 保留 | 理由 |
|---|---|
| 面板头未读徽章（#1）+ 卡片未读轻量标记（#5 改小圆点） | 唯一的"有新东西"扫读信号 |
| 「观察中」/扩展按钮激活与加载态（#2/#3） | 功能开关状态确认 |
| 类别徽章保留**一处**紫色作为域标识（#6），但降为紫字无底（透明底） | 单点标识"这是 AI 主动观察"，与用户消息区隔 |

**R2 其余全部中性化**：卡片折叠头/展开体容器（#4/#7）改用 `--surface` + 单向 `border-top` 分割（对齐「背景分区 + 分割线」规范，同时消除与弹窗卡片感的边界争议）；h3 下划线、`li::marker`、solution label、下拉 hover（#8/#9/#13）改用 `--fg/--muted/--border`；图主输出态（#11）描边改 `--border-strong`、去紫色投影——"主输出"地位由**全幅面积**已经表达，晕影是冗余强调。

**R3 层次一律用排印三件套**：标题 `--fs-13 --fg` 600 / 正文 `--fs-13 --muted` / 注释 `--fs-11 --subtle` + 虚线分隔（§4.3 note 样式即遵循此规则）。**新增色彩使用的唯一豁免**：状态语义色（`--ok/--warn/--rec`）表达客观状态时可用，且遵循"点、线、轻量元素优先"。

**R4 主按钮例外收窄**：卡内"采纳/确认"主按钮（#10）保留实心紫（它是全卡唯一的强动作，符合"色彩只留状态"中的"可操作"半豁免），但普通 action 按钮降为中性描边；若一卡内出现 ≥2 个实心主按钮则属契约违规。

### 6.4 改动面

- 纯 CSS 改动：`recording-view.css` 洞察卡区（L172-213、L282-320）、`RecInsightsPanel.vue` scoped 样式；**不动任何 token 定义**（10 套主题文件零改动），全部改用既有中性 token；
- `is-acknowledged` 降级规则（L288-320）在容器中性化后**大幅简化**——默认态即中性，acknowledged 只需去掉左侧指示条/类别徽章的紫与降 opacity，"让出视觉空间"的逻辑天然成立；
- 对比度核验：note 层 `--subtle` + `--fs-11` 组合需按主题注释惯例核对 WCAG AA ≥4.5:1（`--subtle` 已用于 L167 的 13px 提示文字，风险低但需逐主题过一遍）；
- Mermaid 图内部配色由 `MermaidDiagram.vue` 的 dark/default 主题类控制，不在本节范围（图自身用色属 Board Spec 观察项）。

### 6.5 与分层契约的闭环

收敛后洞察卡的信息架构变为：**排印承担层次（层内可读性），中性面承担分区（块间边界），紫色承担状态（卡间优先级）**——三个通道各司一职，用户"退可略"时看到的是安静的中性版面，"进可查看"时状态色引导他优先处理未读。这与 §1.1 "焦虑来自无法判断值不值得读"的诊断直接对应：颜色克制本质上是把"值得读信号"从通胀中救回来。

## 9. 开放项（需拍板）

1. **决策流节点是否剥离 `（注：…）` 到独立字段**：剥离更干净（节点 `text` 保持纯正文），但需动 todos 形状 schema 与存量兼容读取；不剥离则注释随 content 入节点。提案倾向：**首期不剥离**，④ 期观察真实密度后定。
2. **注释层时间戳引用是否做成可点击跳原文**：洞察侧图节点已有 `@@<ms>` 定位机制可参照，但纪要 Markdown 渲染侧需引入后处理链接化。提案倾向：**首期纯文本**，跳转作为增强项进入观察期。
3. **未读信号收敛后是否足够醒目**：R1 把未读从"紫环+紫底+紫边+左条"降为"小圆点+徽章计数"，若实测反馈"新洞察不够跳"，备选方案是未读卡保留 `--proactive` 左侧 3px 指示条（读后即消失，属状态而非装饰，不违反 R2）——是否启用留待 ④ 期回访确认。
