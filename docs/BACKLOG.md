# BACKLOG — 零散需求与缺陷修复

> 版本主线（v1→v6）见 [ROADMAP.md](ROADMAP.md)。本文收纳开发过程中发现的缺陷与细碎体验优化，完成条目标 ✅。

## 缺陷修复

### ~~修复：录音中绑定人员无效~~ ✅
**目标**：修复在会议纪要录音过程中，绑定说话人后未生效的 bug。

#### 排查方向
- `app/routers/record.py`：`handle_bind_speaker` 事件处理收到前端绑定消息后，需立即更新内存中活跃录音会话的说话人映射（`session.speaker_mapping`），确保后续 WebSocket 推送使用最新映射 ✅
- `core/diarization.py`：`update_speaker_mapping` 方法需同时更新内存映射和持久化到 `data/meeting_mappings.json`，保证映射在会话重启后仍可恢复 ✅

### 纪要页「全屏」按钮无退出入口，且放大后笔记内容丢失
**目标**：修复用户测试反馈——「会议纪要中的窗口放大按钮，点击后全屏展示转写栏，无返回按钮，且用户输入的笔记会丢失」。

#### 现状与根因（两处独立缺陷）
- **无退出入口**：`app/static/index.html` 中 `#genBtnFullscreen` 的点击处理直接调用 `document.documentElement.requestFullscreen()`，进入全屏后按钮图标与 title 仍为「全屏」，不切换为「退出全屏」，界面上无任何可见退出控件，用户只能靠未知的 Esc 键退出。全屏期间当前 Tab 保持为进入前的 Tab（默认态 / 绑定态为转写），用户因此感知为「全屏只剩转写栏」。
- **笔记丢失**：`switchGenTab('notes')` 每次都会调用 `loadTaskNotes()`，异步拉取服务端笔记后执行 `initNotesBlockEditor()` 整体重建块编辑器；而输入保存走 `_notesSaveTimer` 的 1 秒防抖 `saveNotesMarkdown()`。因此未落盘的编辑会被服务端旧内容覆盖，且异步回调可能在用户已开始输入后才返回，直接冲掉正在编辑的内容。统一会议页渲染流程（`renderBindingTranscript()` 之后同样调用 `loadTaskNotes()`）存在同类重建。

#### 修复方向（候选方案待决策）
- 全屏形态二选一：
  - **应用内聚焦模式**：放大当前 Tab 面板铺满工作区、隐藏侧栏与 AI 栏，右上角常驻「退出放大」按钮 + Esc 快捷键；放大的是当前所在 Tab，不跳回转写
  - **保留原生全屏 + 补齐退出入口**：图标与 title 随 `fullscreenchange` 切换、悬浮退出按钮、首次进入时的 Esc 提示气泡
- 笔记保存：切 Tab / 重建编辑器 / 页面隐藏前强制 flush 未落盘内容；`loadTaskNotes()` 增加「本地有未保存修改则不覆盖」保护；异步回填前校验 `currentTaskId` 与编辑器实例是否已失效

### AI 对话框快捷指令点击后不生成内容，且指令按钮永久消失
**目标**：修复用户测试反馈——「在 AI 对话框中点击生成会议纪要功能后，未生成内容，其他功能按钮也消失」。

#### 现状与根因（三处叠加）
- **点击不发送**：`.conv-qcmd` 的点击处理只把 `cmdMap` 里的提示词写入 `convTextarea` 并 `focus()`，不调用 `handleConvSend()`，用户不主动点发送就什么都不会发生。
- **指令区永久消失**：`updateConvCanvasVisibility()` 以 `aiFeed.children.length > 0` 为条件给 `#convCanvasCenter` 加 `is-hidden`，而快捷指令 `#convQuickCmds` 就嵌在画布中心区内。首条消息发出后整块隐藏，且无任何入口可恢复（仅「清空对话」能重现）。
- **语义误命中**：提示词「请根据当前会议内容生成一份结构化会议纪要，包含议题、讨论要点和结论。」中的「结论」被 `app/routers/chat.py` 的 `_detect_action()` 命中 `summarize_conclusions`（关键词按长度计分，「结论」得 2 分且无更长匹配），该动作只回显已有 `task.summary` 前 1500 字，无纪要时返回「该会议尚未生成纪要」，从不触发真正的纪要生成——即用户感知的「未生成内容」。

#### 修复方向（候选方案待决策）
- 快捷指令改为点击即执行：「生成会议纪要」直连 `POST /api/tasks/{id}/retry-summary`（走 qwen-plus 真实生成）并自动切到纪要 Tab；其余指令改为直接发送
- 指令区从画布中心剥离，常驻输入框上方（或收进 `/` 指令面板），发消息后不再消失
- 收紧 `summarize_conclusions` 关键词，避免「生成纪要」类表述被「结论」误命中；必要时新增独立的 `generate_summary` 动作

### 说话人绑定后无法解绑/分离
**目标**：修复实时转写过程中，说话人一旦绑定到某人后无法撤销或重新分配的问题。

#### 现状
用户在录音过程中将某个说话人绑定到特定人名后，如果发现绑定错误，没有「解绑」或「重新分配」的操作入口，绑定关系一旦建立就不可逆。

#### 设计要求
- 转写面板的说话人标签或绑定面板中，提供「解绑」操作
- 解绑后该说话人回到「未分配」状态，可重新绑定
- 已分离的语音段落实例应保留，仅清除绑定关系

### 说话人分离实测极不准确，需优化
**目标**：解决实测中说话人分离质量严重不达预期的问题。这是影响整体产品体验的核心环节。

#### 现状
实测中说话人分离结果与实际参会人数、发言归属存在明显偏差，严重影响纪要可读性和可信度。可能涉及：
- 离线转写：DashScope diarization 过度拆分（一人被识别为多人）或合并不足
- 实时转写：在线聚类阈值导致过度拆分或合并
- 实时侧使用 MFCC 特征（非 CAM++ 嵌入），精度天花板较低

#### 排查方向
- 收集典型 bad case 音频（2 人、4 人、6 人会议各若干）进行复现
- 评估实时侧特征质量升级的可行性与性能影响（参考 ROADMAP v3+ 中期/长期条目）
- 考虑提供「手动修正说话人归属」的交互入口，作为算法精度不足的体验补偿

### 底部状态栏「云端 AI 服务已连接」为静态文案，与真实路由不符
**目标**：修复 UI 缺陷——底部状态栏在任何状态下都宣称「云端 AI 服务已连接」，与登录态、云端配置、LLM 实际路由均无关。全本地（Ollama）运行、零出网时该文案与「本地 Ollama 时零出网」隐私承诺（`frontend/src/i18n/*/settings.json` engine_cell_llm_context_local）直接冲突，侵蚀用户信任。

#### 现状与根因
- `frontend/src/App.vue:113` 写死绿点 pip + `t('common.usage.cloud_connected')`（「云端 AI 服务已连接」），无响应式数据源；登录遮罩、非登录、本地端点下均恒显已连接。
- 真实判据已存在但未被该 UI 引用：`is_cloud_enabled()`（`core/cloud_client.py:43`，按 CLOUD_API_URL+TOKEN 判定）、用户登录态、`GET /api/settings` 返回的 `llm.provider/base_url`。

#### 设计要求
- 状态栏该项改为展示纪要 LLM 实际路由，三态：`本地引擎（Ollama / LM Studio）` / `云端服务` / `未配置（点击进入设置）`；数据源复用现有 `GET /api/settings` + 登录态，**无需新增后端接口**。
- 本地引擎判定：`llm.base_url` 的 host 为 `localhost` / `127.0.0.1`。
- 点击该项跳转 设置 → 计算引擎 Tab。
- i18n 新增三态键，废弃恒真文案键。

#### 建议排期
与 [PRD-LOCAL-ENGINE](PRD-LOCAL-ENGINE.md) WP-A（R4 LLM 自接增强）同域，建议并入 WP-A 一并交付（R6 已有「引擎徽章三态」语义，本条是其底部状态栏投影）。

### 说话人绑定「新建」入口优化
**目标**：解决说话人列表过长时「新建说话人」被挤到底部、难以触达的问题。

说话人绑定弹窗中，「新建说话人」固定渲染在列表底部。当说话人数量较多（10+）时，用户必须持续滚动才能找到新建入口，操作效率低。

### 顶部菜单精简
**目标**：顶部菜单要克制，更多信息留给内容而不是功能。这是软件的设计范式。

#### 设计原则
- 菜单栏只保留高频、不可缺少的操作，低频功能下沉到右键菜单或设置页
- 内容区域优先于功能区域——用户打开会议纪要是为了阅读，不是为了点按钮
- 减少视觉噪声，让信息密度回归内容本身

### AI 对话面板消息类型增强
**目标**：AI 面板从「纯文本气泡」升级为「过程可见、结果可操作」的 Agent 交互，让用户看得到系统在做什么，且 AI 产出可直接操作。

#### 现状
AI 面板消息流目前只有纯文本气泡；工具调用过程、结构化结果、原文引用等 Agent 信息缺失，无法体现对话驱动操作的产品定位。

#### 消息类型规划（按优先级）
- **P0 · 工具调用卡片**：AI 调用后端工具（转写/纪要生成/待办提取）时展示过程卡片——可折叠，完成后收起为一行摘要；显示耗时；失败变红并提供重试按钮
- **P0 · 结构化结果卡片**：待办/结论渲染为可操作卡片——待办项可勾选、可导出到日历；结论项可引用跳转转写原文；支持一键复制
- **P1 · 上下文引用块**：AI 回答涉及会议内容时显示引用来源（说话人 + 时间戳 + 原文摘录），点击跳转转写面板对应位置，可选播放原声
- **P1 · 进度指示器**：长任务展示分阶段流水线状态（✓ 已完成 / ⏳ 进行中 / ○ 待执行 + 各阶段耗时），降低排队焦虑
- **P2 · 快捷指令结果预览**：`/待办` `/结论` 等快捷指令返回结构化卡片（标题 + 要点列表 + 展开详情 / 导出 Markdown）
- **P2 · 侧边栏会话列表增强**：列表卡片增加对话轮数、待办数量、最后一条摘要（悬停显示）、后台任务完成未读标记

#### 依赖与约束
- 结构化结果卡片、进度指示器依赖后端暴露细粒度的任务阶段事件（现有轮询接口可能需要扩展）
- 上下文引用块需要转写原文的句级时间戳数据（转写结果已含），并与转写面板建立双向导航

### 会议纪要归档到项目文件夹
**目标**：让会议纪要成为项目资料的有机组成部分，以 AI 工具友好的结构化格式归档到项目目录下，使 AI IDE（Qoder、Cursor 等）的 Agent 在扫描项目文件时能快速理解会议上下文——讨论了什么、决定了什么、要做什么。

#### 背景
当前会议纪要仅存储在本应用的 `data/tasks/` 目录中，虽然通过 `project_id` 关联了项目，但产出内容对外部工具不可见。用户希望会议纪要能以结构化 Markdown 文件的形式落入项目文件夹，与项目文档并列，形成完整的知识资产。更关键的是，这些文件需要被 AI 编程助手（如 Qoder）在分析项目时自动发现和解析，让 AI 能立即理解项目的决策历史和行动项。

#### 核心设计

**1. 项目设置：是否允许归档**
- 项目数据模型新增 `meeting_archive` 配置项：
  ```json
  "meeting_archive": {
    "enabled": false,
    "subfolder": ".meetings",
    "format": "summary"
  }
  ```
- `enabled`：总开关，默认关闭。用户需显式开启才写入
- `subfolder`：归档子目录名（相对于项目文件夹根路径），默认 `.meetings/`（以 `.` 开头避免干扰正常文件浏览）
- `format`：归档内容粒度
  - `summary`：仅纪要摘要 + 待办
  - `full`：摘要 + 章节 + 待办 + 转写原文
  - `minimal`：仅摘要

**2. AI 工具友好的文件格式规范**

**设计原则**：文件同时服务于「人类阅读」和「AI 快速解析」两个场景。AI Agent 通常先扫描 Front Matter 判断文件相关性，再按需读取正文。格式必须标准化，让任何 AI 工具无需猜测结构。

**文件命名**：`{meeting_date}_{title}.md`（如 `2026-09-06_财务星瀚需求对齐.md`）

**Front Matter（YAML）**：AI Agent 的第一眼判断依据
```yaml
---
title: "财务星瀚需求对齐"
description: "与财务团队对齐星瀚系统全面预算模块的技术方案，确认接口规约和数据迁移策略。"
type: meeting
created_at: "2026-09-06"
meeting_date: "2026-09-06"
duration_minutes: 45
participants: ["张三", "李四", "王五"]
task_id: "abc123"           # 回溯到本应用的完整数据
tags: ["财务", "预算", "技术方案"]
category: "technical"
status: "published"
# AI 快速摘要——Agent 仅读此字段即可判断是否需要深入
ai_context: "确认了星瀚预算模块采用 RESTful API 对接，数据迁移分三期完成，首期处理历史科目映射。张三负责接口文档，李四负责迁移脚本。"
---
```

**正文结构（固定章节，AI 可按 section 精准提取）**：
```markdown
## 摘要
（一段话概括会议核心结论）

## 关键决策
- **决策 1**：采用 RESTful API 对接星瀚预算模块
  - 依据：团队熟悉度高，维护成本低
  - 反对方案：gRPC（性能优势在当前规模下不明显）

## 行动项
<!-- 结构化 action items，AI 可直接提取为待办 -->
- [ ] @张三 输出接口文档 — 截止 2026-09-10
- [ ] @李四 编写数据迁移脚本 — 截止 2026-09-15
- [x] @王五 确认科目映射规则（已完成）

## 讨论要点
### 议题 1：接口规范
（讨论细节...）

### 议题 2：数据迁移策略
（讨论细节...）

## 相关信息
- 关联项目：财务星瀚项目
- 参考资料：`docs/API_CONTRACTS.md`
```

**为什么这样设计**：
- `ai_context` 字段：AI Agent 仅扫描 Front Matter 即可获得会议全貌，无需解析全文。这是最关键的优化——类似于代码文件的 JSDoc/docstring，让 AI 在文件索引阶段就能判断相关性
- 固定章节标题：AI 可按需跳转（只读「关键决策」或只读「行动项」），降低 token 消耗
- `type: meeting` 标签：让 AI 工具立即识别文件类型，区别于技术文档、设计文档等
- 行动项使用 Markdown checkbox 语法：GitHub/IDE 原生渲染，AI 可直接提取为 TODO
- Front Matter 遵循项目已有的 Metadata.md 规范（title/description/tags/category 等必填字段），与项目其他文档风格一致

**3. 归档触发时机**
- 纪要生成完成后，若关联项目开启了归档功能，**不自动写入**，而是弹出确认提示：「是否将纪要和待办写入项目文件夹？」，由用户选择是否执行
- 提示内容应明确告知用户：写入目标路径、写入内容范围（纪要/待办/全部）、是否覆盖已有文件

### 实时摘要自动更新倒计时与刷新频率自定义
**目标**：解决用户测试反馈——「会议实时录制时，右侧实时摘要的刷新存在感知空白，需要自动更新倒计时功能，并支持用户自定义刷新频率」。

#### 现状
- **后端刷新间隔硬编码**：`core/realtime_summary.py` 的 `SUMMARY_INTERVAL = 60`（60 秒）为模块级常量，无法在运行时调整
- **前端无时间反馈**：实时总结面板状态栏（`#recSummaryStatus`）仅显示「等待中 / 总结中... / 已更新 / 已暂停」纯文字，用户无从得知距下次刷新还有多久
- **感知空白**：两次摘要推送之间（最长 60 秒 + LLM 调用耗时）面板完全静止，用户误以为功能失效或卡死

#### 设计要求

**1. 自动更新倒计时**
- 实时总结面板 header 区域显示倒计时（如「下次更新：42s」或环形进度条），从上次总结完成开始计时
- 倒计时归零后切换为「总结中...」状态（现有逻辑），完成后重置倒计时
- 暂停状态下倒计时冻结，恢复后继续
- 页面刷新/重连时，后端需同步当前定时器剩余秒数（通过 WebSocket 回放消息或新字段 `remaining_seconds`）

**2. 用户自定义刷新频率**
- 设置页「功能开关」区域中「实时总结生成」开关旁增加频率选择器
- 候选频率：30 秒 / 60 秒（默认）/ 120 秒 / 300 秒
- 配置持久化到 `data/settings.json` 的 `feature_flags.realtime_summary_interval` 字段
- 后端 `RealtimeSummarizer` 构造时接收 `interval` 参数替代模块常量；录音中修改频率需评估是否立即生效（热更新 vs 下次录音生效）

#### 实现要点
- **后端**：`RealtimeSummarizer.__init__` 新增 `interval: int = SUMMARY_INTERVAL` 参数；`_schedule_next()` 使用该实例属性；WebSocket 回放增加 `summary_countdown` 消息类型（含 `remaining` 字段）
- **前端**：`handleSummaryStatus('idle')` 时启动 `setInterval` 倒计时渲染；`handleSummaryStatus('summarizing')` 时停止倒计时
- **设置页**：频率选择器变更调用 `PATCH /api/settings/feature-flags` 写入 `realtime_summary_interval`

#### 约束
- 频率过低（<30s）会导致 LLM API 调用频繁，需设下限防止滥用
- 倒计时精度允许 ±1 秒偏差（前端 `setInterval` 与后端 `threading.Timer` 不完全同步可接受）
- 与「功能开关：实时总结」条目联动——开关关闭时倒计时 UI 一并隐藏

### 转写内容支持删除，并按删改后的原文刷新纪要

### ~~说话人绑定体验闭环~~ ✅
**目标**：消除实时绑定与批处理之间的体验断裂，用绑定文本作为最高优先级匹配证据，声纹更新由系统自动完成并让用户感知采集机制。对应 ROADMAP v3++。

#### 背景
实时绑定与批处理是两条独立管线。用户在录音阶段完成绑定后，批处理重新做说话人分离，产出全新的 `speaker_id`，此前绑定被覆盖。两阶段说话人分离数量可能不一致，ID 映射无法直接对齐。

但实时绑定过程中产出了两类可跨阶段复用的资产：
- **绑定文本内容**（确定性证据）：用户绑定的说话人说了什么文本，这些文本在批处理结果中仍可被搜索到
- **声纹特征向量**（概率性证据）：绑定时的音频片段提取的声纹，跨阶段稳定

当前代码中声纹采集→存储→自动匹配的链路已完整存在（`core/voiceprint.py` + `app/store.py:673-699`），但缺少文本桥接匹配和声纹自动更新。

#### 设计要求

**1. 实时转写全量保留**
- 新增 `realtime_full_transcript` 字段，持久化完整实时转写记录（含 speaker_id、文本、时间戳）
- 突破当前 `REALTIME_BUFFER_MAX = 10` 的限制
- 涉及文件：`app/store.py`、`app/routers/record.py`

**2. 文本桥接匹配（P0 优先级）**
- 批处理完成后，找到实时阶段某已绑定说话人的所有文本片段
- 在批处理结果的 dialogue 中搜索相同或高度相似的文本
- 看它们被归到了哪个新 `speaker_id`，直接继承绑定关系
- 匹配逻辑可新增 `core/text_bridge.py` 或在 `core/voiceprint.py` 中新增函数

**3. 分层匹配策略**
- P0：文本内容匹配（确定性证据，实时阶段有绑定 + 文本被保留时可用）
- P1：声纹向量匹配（概率性证据，声纹库有注册 + 置信度达标时可用）
- P2：用户手动绑定（兜底，以上均无结果时）
- 在 `app/store.py:_run_stage2_for_task()` 中按优先级依次执行

**4. 声纹自动更新 + 时长加权**
- 每次确认说话人身份后（自动匹配或手动绑定），系统自动用该说话人的音频片段更新声纹注册表
- `sample_count` 改为 `total_sample_duration`（秒），累积平均按音频时长加权
- 移除设置页面的手动「更新声纹」按钮
- 涉及文件：`core/voiceprint.py:register_voiceprint()`

**5. 声纹采集用户感知**
- 实时绑定完成后，提示「已记录声音特征，后续会议将自动识别」
- 设置页说话人列表显示「声纹样本：X 分钟」（替代更新按钮）
- 批处理自动匹配成功时，提示「根据声音特征自动识别了 N 位说话人」
- 首次进入绑定态时暗示「系统正在学习识别说话人」，降低用户对「绑定结果会被保留」的预期

#### 实现路径
1. `app/store.py`：新增 `realtime_full_transcript` 字段，录音期间持久化完整实时转写记录
2. `app/routers/record.py`：实时转写消息处理时同步累积到全量记录
3. `core/voiceprint.py`：`register_voiceprint()` 支持时长加权；`sample_count` → `total_sample_duration`
4. `app/store.py:_run_stage2_for_task()`：批处理完成后先跑文本桥接匹配，再跑声纹匹配，最后降级到手动绑定
5. `app/static/index.html`：设置页移除「更新声纹」按钮，改为显示声纹样本时长；自动匹配成功时的提示文案调整

#### 依赖与约束
- 依赖现有声纹注册表（`data/voiceprint_registry.json`）和自动匹配链路（`voiceprint.auto_identify_speakers()`）
- 文本桥接匹配依赖实时转写文本的完整保留，需评估内存和存储开销
- 涉及文件：`app/store.py`、`app/routers/record.py`、`core/voiceprint.py`、`app/static/index.html`

### 实时录音界面显示系统时钟
**目标**：录音界面除了显示录制时长，还应展示用户电脑上的系统时钟，让用户感知真实世界的时间。

#### 现状
录音界面仅显示录制时长计时器（如「00:23:45」）和录音开始的时间点信息，用户无法直观感知当前时刻。

#### 设计要求
- 录音界面持续显示系统时钟（如「14:30:25」），而非仅显示录音时长
- 会议开始时间、结束时间以系统时钟为准，用户一眼可知「几点开始、几点结束」
- 各事项（转写段落、章节切分、笔记等）发生的时间也能与系统时钟对应
- 时长计时器保留，但系统时钟作为主要时间参考

### AI 主动识别会议卡壳与偏题
**目标**：AI 从被动记录者转变为主动参与者，在会议陷入僵持或偏离主题时主动介入。对应 PRD「演进方向：从会议助理到主动型 AI」。

#### 设计要求
- **卡壳场景**：当会议围绕一个问题无法得出结论、讨论陷入循环时，AI 主动提供解决方案或建议
- **偏题场景**：AI 检测到讨论偏离会议主题时，主动提醒并引导回归
- **呈现方式**：AI 建议以折叠的未读卡片形式出现在消息栏，不打断会议进行，用户按需查看
- **时间轴关联**：卡片能与转写时间轴关联并交互，点击可跳转到对应讨论位置
- 需要定义「卡壳」「偏题」的识别策略（基于上下文语义分析）
- 考虑用户可控的介入程度设置（如开关、灵敏度）

### 实时总结功能重新定位
**目标**：总结能力本身是产品必需的，但当前实现形态鸡肋，需要找到更有价值的新方向。

#### 核心判断
**总结能力需要保留，问题在于当前形态**。用户不是不需要总结，而是当前「分钟级增量摘要」的独立面板形态没有实际用处。需要重新思考总结应该以什么形式、在什么时机、解决什么问题。

#### 现状
- 实时总结（`core/realtime_summary.py`）在录音过程中按分钟级增量生成摘要，但用户反馈「没什么用」
- 已有「对话框总结类指令与实时总结职责重叠」条目（见上方）指出职责不清
- 实时总结、对话框总结指令、纪要生成三处产出重叠且互不引用
- 与「主动型 AI」方向结合看，实时总结可能是「主动介入」的候选载体，但当前形态价值不足

#### 设计要求（待决策）
- 先明确「实时总结」与「纪要」「章节」的差异化定位，避免产出重叠
- 候选方向：
  - 与「主动型 AI」结合：实时总结升级为「会议状态感知」，不再只是摘要，而是提供洞察（卡壳提醒、进度总结、待确认事项）
  - 精简为行内摘要：不再独立面板，而是嵌入转写流中的轻量摘要标记
  - 与章节生成合并：统一为「会议脉络」，同时提供结构 + 摘要
- 关键原则：不是砍掉总结能力，而是找到用户真正有用的呈现方式和触发时机

### 笔记支持选中文本添加批注
**目标**：笔记功能除了手动输入发送外，还应允许用户选中转写内容并添加批注，让笔记与会议原文建立关联。

### 转写摘要允许用户编辑
**目标**：转写过程中产出的摘要应允许用户参与编辑，用户参与上下文后对产出的置信度更高。对应「企业化核心洞察」。

**功能描述**：

**功能描述**：

- 使用 `ResizeObserver` 检测工具栏可用宽度，动态计算降级级别

**业务价值/目的**：确保不同屏幕尺寸下工具栏始终可用且不溢出，消除窄屏场景的操作障碍。作为全局设计规范统一各页面行为，降低后续开发的决策成本。

#### 4. 说话人手动标记准确性修复

**功能描述**：
修复手动标记/绑定发言人时存在的逻辑 Bug：当用户对某段对话手动指定发言人后，系统错误地将其他不相关的对话段落也归属到同一发言人，导致转写结果中说话人归属大面积失真。

问题根因排查方向：
- `core/diarization.py` 或 `app/routers/record.py` 中的绑定逻辑可能将局部绑定错误地扩散为全局映射
- 说话人 ID 映射表（`speaker_uuid_mapping`）更新时，可能未限定作用范围（时间区间或段落级别）

修复要求：
- 手动绑定仅对目标对话段落（或用户选定的时间区间）生效，不影响其他不相关的对话段落
- 绑定操作的作用范围需明确：基于时间邻近性或段落选择范围确定影响区域
- 确保说话人映射的数据隔离——手动绑定结果与自动聚类结果互不干扰

**业务价值/目的**：说话人归属的准确性是转写结果可信度的基础。此 Bug 直接导致用户无法信任手动修正的结果，修复后保障说话人分离与绑定的精确性。

**关联条目**：上方「说话人绑定后无法解绑/分离」「说话人分离实测极不准确」「说话人绑定体验闭环」（共同构成说话人管理准确性与体验的完整闭环）

### 三、AI 能力与上下文增强

#### 5. AI 操作交互确认机制

**功能描述**：
当 AI 助手在对话中需要执行系统级操作（如 CLI 命令、文件操作、配置修改等）时，当前流程缺少用户确认环节，存在误操作风险。需增加交互确认步骤。

交互流程：
- AI 解析用户意图后，若涉及 CLI 命令执行或系统级操作，先在对话气泡中以「操作预览卡片」形式展示：命令内容、预期影响范围、可能的风险
- 用户需显式点击「确认执行」或「取消」
- 确认后才实际执行操作，执行结果回显在对话中
- 可选：对高频可信操作提供「始终信任此类操作」选项，减少确认疲劳

**业务价值/目的**：防止 AI 误判用户意图导致不可逆操作（如删除文件、修改配置），提升用户对 AI 驱动操作的信任感和安全感。

**关联条目**：上方「AI 对话框快捷指令点击后不生成内容」（同为 AI 对话交互可靠性优化）、「AI 对话面板消息类型增强」（操作确认卡片可作为新的消息类型）

#### 6. 纪要编辑与上下文反馈增强

**功能描述**：
支持用户直接编辑 AI 生成的会议纪要/摘要，并将编辑后的内容作为高置信度上下文反馈给大模型，提升后续 AI 生成和问答的准确性。

功能分为两层：

**第一层 · 纪要可编辑**：
- 纪要 Tab 内容支持 inline 编辑（富文本或 Markdown 编辑模式）
- 编辑后自动保存，持久化为「用户修正版」
- 保留「原始 AI 生成版」与「用户编辑版」两个版本，支持对比查看或一键回滚
- 编辑入口明显（如「编辑」按钮切换只读/编辑态），编辑态有明确的视觉区分

**第二层 · 编辑内容作为高置信度上下文**：
- 用户编辑后的内容在后续 AI 对话和纪要重新生成时，作为最高优先级的上下文注入
- 具体实现：编辑内容标记为「用户确认事实」，LLM prompt 中以系统指令形式注入（如「以下为用户修正的会议结论，请以此为准」）
- 效果：后续基于该纪要的 AI 问答、二次生成、待办提取等均以用户编辑版本为基准，避免 AI 重复产出已被用户修正的错误内容

**业务价值/目的**：让用户从被动接受 AI 产出转变为主动参与内容修正，提升对产出结果的信任感（呼应 PRD「企业化核心洞察：用户参与上下文后对产出置信度更高」）。编辑内容作为高置信度反馈，形成「AI 生成 → 用户修正 → AI 学习」的正向循环。

**关联条目**：上方「转写摘要允许用户编辑」（共享编辑组件和上下文反馈机制，可合并实现）、「实时总结功能重新定位」（总结/纪要的编辑能力统一规划）

#### 7. 实时章节折叠交互

**功能描述**：
实时转写/纪要界面中，AI 自动划分的「章节（Chapters）」目前平铺展示，内容较多时信息密度过高，用户难以快速定位和浏览。需支持章节的折叠/展开操作。

交互设计：
- 每个章节标题行可点击，切换折叠/展开状态
- 折叠态：章节标题保持可见，标题旁显示折叠箭头图标（▶），标题下方显示一行摘要预览（取章节首句或 AI 生成的章节摘要，截断至 60 字）
- 展开态：显示完整章节内容（转写文本 + 章节摘要），箭头图标变为向下（▼）
- 默认行为：当前进行中的章节保持展开，历史章节自动折叠，减少视觉噪声
- 支持「全部展开/全部折叠」的批量操作按钮
- 功能受「实时章节生成」功能开关控制——开关关闭时折叠 UI 一并隐藏

**业务价值/目的**：提升实时转写界面的信息组织效率，用户可快速浏览章节结构、按需深入查看细节，避免长文本带来的信息过载。

**关联条目**：上方「功能开关：实时章节与总结」（折叠 UI 受功能开关控制）

#### 8. 实时新词发现与确认机制

**功能描述**：
实时转写过程中，当 ASR 引擎识别到未在热词表中注册的专有名词（人名、项目名、术语等）时，可能错误识别或跳过。需提供新词发现机制，让用户实时确认和注册新词。

交互流程：
- **检测**：实时流中，当 ASR 返回低置信度识别结果或上下文语义暗示新专有名词时，系统在转写面板中以高亮样式标记疑似新词
- **提示**：高亮词旁出现可点击的小气泡或下划线提示（如「疑似新词：星瀚系统」），点击弹出确认对话框
- **确认操作**：
  - 「添加为热词」：将该词加入热词表（`data/hotwords.txt`），后续识别立即生效
  - 「忽略」：本次忽略，不加入热词表
  - 「编辑」：修正识别结果（如 ASR 识别为「星汉系统」，用户修正为「星瀚系统」）
- **频率控制**：同一新词在一次会议中最多提示一次，避免反复打扰
- **可选 · 暂停模式**：当用户选择处理新词时，可选择暂停录音流，专注处理后再恢复（适用于需要仔细确认的场景）

**业务价值/目的**：解决专业术语/人名识别不准的痛点，让用户在录音过程中即时纠正，而非事后批量修正。通过人机协作持续提升热词系统准确性，是产品差异化能力之一。

**关联条目**：与现有热词管理系统（`core/hotwords.py`）深度集成，复用热词 API

### 四、外部集成

#### 9. 本地系统日历集成

**功能描述**：
探索并实现读取本地系统日历（优先 macOS 日历）的能力，在应用内展示用户未来的会议安排，方便用户从日历事件一键发起录音。

功能细节：
- **日历读取**：通过 macOS 系统 API（EventKit framework 或 `icalBuddy` CLI 工具）读取本地日历事件
- **展示**：在应用内新增「日历」视图或侧边栏区域，展示未来 N 天（默认 7 天）的会议安排，包含会议标题、时间、地点、参与者等信息
- **一键发起录音**：从日历事件卡片点击「开始录音」，自动创建新的录音任务，预填充会议标题和关联信息（如参与者列表可映射到说话人档案）
- **权限管理**：首次访问时请求日历读取权限，权限拒绝时给出清晰引导
- **隐私考量**：仅读取用户显式授权的日历，支持选择特定日历源（如仅读取「工作」日历，不读取「个人」日历）

**业务价值/目的**：打通「日历 → 录音」的工作流入口，让用户从会议安排直接发起录音，减少手动操作步骤。与 PRD 演进方向「从被动工具到主动助手」呼应——日历集成是「会前感知」的第一步，为后续「会前提醒」「自动发起录音」等主动能力奠定基础。

**关联条目**：与 PRD「演进方向：从会议助理到主动型 AI」呼应；技术实现涉及 macOS 系统 API，需评估跨平台兼容性（Windows 打包后日历集成方案）
