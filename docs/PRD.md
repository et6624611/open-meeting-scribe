# PRD — 产品需求

本文沉淀版本无关的稳态需求，随产品演进原地更新。

## 1. 目标用户
- 需要频繁开会、且要手动整理纪要的个人。

## 2. 核心场景
| 场景 | 描述 | 版本 |
|------|------|------|
| 线上会议内录 | 腾讯会议/飞书等，一键录制系统声音 → 结束自动出纪要 | v1 (P2) |
| 音频文件转写 | 拖入已有录音（wav/mp3/m4a）→ 出纪要 | v1 (P1) |
| AI 对话驱动 | 通过自然语言对话完成录音、转写、查询、设置等操作 | v1 (P2) |
| 发言人姓名化 | 「说话人1」自动变「张三」 | v3/v4 ✅ |

## 4. 产品定位 · AI 对话是标配

AI 对话框不是附加组件，而是产品的**核心交互范式**：

| 维度 | 说明 |
|------|------|
| 交互方式 | 自然语言驱动全流程，降低学习成本 |
| 设置入口 | 对话可直接修改配置（模型、热词、API Key） |
| 上下文感知 | 对话与当前会议状态联动，支持追问 |
| 长期演进 | 从被动响应 → 主动助手（会前提醒、会中摘要、会后跟踪） |

### 演进方向：从会议助理到主动型 AI

当前产品定位是「被动式会议助理」——用户发起录音、触发转写、请求纪要。未来产品应从**被动工具**向**主动型 AI** 转变，聚焦 AI 会话领域：

| 维度 | 当前（被动） | 未来（主动） |
|------|-------------|-------------|
| 角色 | 忠实记录者 | 会议参与者 |
| 卡壳识别 | 无 | AI 检测到议题僵持不下时，主动提供解决方案 |
| 偏题识别 | 无 | AI 检测到讨论偏离主题时，主动提醒并拉回 |
| 产出形式 | 用户主动请求才生成 | AI 建议以折叠未读卡片出现在消息栏，用户按需查看 |
| 时间轴关联 | 无 | AI 产出与转写时间轴双向关联，可点击跳转定位 |

### 企业化的核心洞察

软件从私人使用走向企业的核心价值：**更大的上下文让会议走向和决策更加有效**。企业场景下会议涉及的背景资料、历史决策、参与人关系等上下文远比个人场景丰富，AI 能基于更完整的上下文提供更有价值的分析和建议。这也意味着转写摘要等环节应允许用户参与编辑——用户参与上下文后，对产出内容的置信度更高。

### 生态闭环：做跨平台的中立枢纽

会议软件（腾讯会议/飞书）与转录工具分属两个生态，接缝在三处：**会前**缺会议元数据（谁参会 / 什么会 / 议程），**会中**靠内录「隔墙」采集、参会人无法自动关联，**会后**纪要与待办回流不到人们真正干活的协作工具。

本产品使命是「摆脱生态锁定」（见 [MISSION.md](../MISSION.md)）。因此闭环方向**不是**接入某个平台的开放 API 做深度集成——那会自相矛盾，把自己降级为平台附庸；而是做**跨平台中立枢纽**：上游兼容任意音频与上下文来源，下游回流到任意协作生态，闭环握在自己手里。

| 缝合点 | 策略 | 锚点 |
|--------|------|------|
| 会前 · 上游补上下文 | 靠「项目」机制沉淀议程 / 参会人 / 历史决策，上下文归自己掌控，跨平台通用 | MISSION「纪要孤立」痛点 |
| 会中 · 主动型 AI | 基于音频流而非平台 API 进入会中（卡壳 / 偏题识别），是唯一不违背反锁定使命的越界方式 | 本章「演进方向」 |
| 会后 · 下游回流 | 待办 → 任务系统、纪要 → 企业微信文档 / 邮件，输出端「到处能去」，输入端才「到处能来」 | ROADMAP 想法池 |

**边界**：不追求成为任何会议平台的插件。会议软件应始终是「可替换的音频源之一」，协作工具是「可分发的下游之一」——你站在中间，闭环才在你手里。

## 5. 验收标准
- 给一段真实中文多人会议音频，产出**含发言人、可读、带结论与待办**的 Markdown 纪要。

## 6. 非目标（v1）
- 本地语音解析（v2 再议）、多语种、实时字幕。
