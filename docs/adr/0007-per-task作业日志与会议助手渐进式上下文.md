# ADR-0007 per-task 作业日志与会议助手渐进式上下文

- 状态：Accepted
- 日期：2026-09-04
- 相关：core/joblog.py、app/store.py、app/routers/chat.py、app/routers/speakers.py
- 依赖：ADR-0005（说话人姓名化）

## 背景

会议助手（AI 对话）此前仅注入实时转写、会议元信息、项目资料、对话历史四个维度，缺少该会议「操作与运行」的痕迹。助手面对「为什么声纹没匹配」「纪要为何失败」「刚才做了什么」这类问题时只能凭元信息自由发挥，甚至给出与代码行为相反的结论（如单人会议被答成「无需声纹匹配」，而代码实际会跑匹配）。

全局 `logs/server.log` 噪声大（含 HTTP 访问行）且非按会议组织；`CHANGELOG.md` 记录的是迭代规则而非单次会议的执行痕迹。二者都不适合作为 per-meeting 的助手上下文。

## 决策

1. **新增 per-task 作业日志层** `core/joblog.py`：append-only JSONL（`data/tasks/{id}.joblog.jsonl`），以 task_id 为键记录事件（`ts/stage/level/message/detail`）。作业日志**从属于会议纪要**——会议助手针对某会议提问时，加载的正是该会议此前发生过的操作与运行痕迹。
2. **埋点收敛在关键节点**：`store.py` 管线 stage1/stage2、声纹匹配命中/降级/失败、等待绑定、失败与重试；`speakers.py` 确认绑定；`chat.py` 助手动作执行结果。不记 HTTP 与逐句转写噪声。
3. **会议助手渐进式注入**（chat.py 维度 2.5）：
   - 意图门控——仅当问题涉及操作/运行/流程/故障（`JOBLOG_INTENT_KEYWORDS`）才加载，即「某些情况」；
   - 第一层轻量概要——阶段计数 + 最近若干条事件；
   - 第二层按需明细——按问题检索相关事件（stage 触发词 + 子串命中），限条数。
   不全量日志塞入提示词。
4. **旁路降级**：作业日志写入/读取失败静默降级（仅告警日志），绝不打断转写/纪要主链路。

## 后果

- 正面：助手回答操作/故障类问题有据可依，可回溯该会议真实执行痕迹（含助手自己执行过的动作）；上下文体积可控。
- 代价：新增一类 per-task 数据文件，需随任务清理；意图关键词门控存在漏判（措辞不在表内则不注入），策略为宁可漏注入、不塞噪声。
- 否决的替代方案：
  - 全量 `server.log` 注入——噪声大、非 per-meeting、体积不可控；
  - `CHANGELOG.md` 注入——记录迭代规则而非单次会议执行，答非所问；
  - function-calling 多轮取日志——改造大，v1 单轮请求-响应架构不引入。
