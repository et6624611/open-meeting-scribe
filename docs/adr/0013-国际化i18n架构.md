# ADR-0013：国际化（i18n）架构

- **状态**：已接受（2026-09-10）
- **关联**：CHANGELOG `[v2.x-i18n-foundation]`、`docs/ARCHITECTURE.md`「国际化」模块

## 背景

产品计划支持灵活的多语言适配。改造前：前端 22 个 Vue 组件 + 25 个 TS 模块的 UI 文案全部中文硬编码；后端 12 个 router 的 `HTTPException` detail、响应 message、`core/errors.py` 错误建议也均为中文硬编码。需要一套前后端一致、可增量推进、类型安全且低运行时开销的 i18n 方案。

## 决策

### 前端：vue-i18n v11（Composition API 模式）

- 选 `vue-i18n@^11.4.0` 而非 i18next/petite-vue-i18n：Vue 官方生态、`createI18n` 泛型类型推导可在编译期校验翻译键、`@intlify/unplugin-vue-i18n` 与现有 Vite 6 构建链无缝集成并预编译语言文件。
- `legacy: false`（Composition API），locale 由 i18n 实例统一管理，**不存入 Pinia**（避免 `$t` 响应式失效）。
- 语言文件按模块拆分为 15 个 JSON（common/recording/start/... ai-panel），en 静态导入（默认语言零延迟），其他语言经 `import()` 动态加载并由 Vite 自动分包。
- 语言检测优先级：localStorage > `navigator.language` > 默认 en。
- 非组件 TS 文件（composables/stores）无法用 `useI18n()`，故 `i18n/index.ts` 额外导出走全局 composer 的 `tt()` 函数。

### 后端：Babel + gettext，msgid 用英文

- 选 Babel + gettext 而非 python-i18n/fastapi-babel：`pybabel extract` 可自动扫描 `_()` 生成 `.pot`，`.mo` 二进制编译运行时零解析开销，`.po` 可对接 Crowdin/Transifex 等翻译平台。
- **msgid 统一用英文原文**，`.po` 翻译到目标语言；缺翻译时 fallback 为可读英文。
- `I18nMiddleware` 按优先级解析语言：查询参数 `?lang=` > Cookie `locale` > `Accept-Language` 头 > 默认 en。

### 关键：`_()` 由 ContextVar 驱动（请求级 locale）

后端多数 router 函数与 `core/errors.py` 的深层调用栈**不接收 `request` 参数**，无法用 `request.state.gettext`。故参照 `core/users.py` 的 `set_request_user_id` ContextVar 模式：

- 中间件在请求开始 `set_current_locale(locale)`、`finally` 中 `reset_current_locale(token)`；
- `_()` 读取 ContextVar 当前值，无请求上下文（脚本/后台任务）时回退默认 locale；
- WebSocket 不走 HTTP 中间件，处理器内手动 `set_current_locale(locale)`（locale 由前端 `?locale=` 传入）。

这样 router 内 `raise HTTPException(404, _("Task not found"))` 与 `core/errors.py` 的 `_()` 无需传 request 即获请求级语言。

### 前后端联动

- `api/client.ts` 请求拦截器自动为每个请求附加 `Accept-Language`（值取自当前 i18n locale）。
- WebSocket 连接 URL 附加 `?locale=`。
- 设置页「语言」分区提供 zh-CN/English 一键切换，持久化到 localStorage。

## 翻译边界（刻意不翻译的部分）

| 类别 | 决策 | 理由 |
|------|------|------|
| 持久化的 `tasks[task_id]["message"]` | **不后端翻译** | 避免把某请求者语言烤进磁盘数据；前端已有 `common.status.*` 经 `getStatusLabel()` 渲染 |
| 后台线程内推送的 WS 消息 | 不翻译 | ContextVar 不跨 `threading.Thread` 传播，线程内 `_()` 只会拿到默认 locale |
| chat.py 的 AI 动作结果 message / prompt | 保留中文 | 属模型输入/工具输出而非纯 UI，翻译可能干扰 AI 语义 |
| 日志串（logger.*） | 保留中文 | 面向开发者诊断，非用户界面 |
| 前端演示 mock 数据、AI 自动分组内部组名判别符 | 保留 | 属数据/内部逻辑键，翻译会破坏自比较逻辑 |

## 翻译工作流

- 后端：`pybabel extract -F babel.cfg -o messages.pot app/ core/` 自动收集 `_()` → `scripts/gen_i18n_po.py` 按「英文→中文」映射表生成 `zh_CN.po`、en 用 identity 生成 `en.po` → `pybabel compile` 编译 `.mo`。
- 前端：`vue-tsc` 类型检查保证 `t()` 键存在；手动维护各模块 JSON（zh-CN 为源，en 对齐）。

## 后果

- **正面**：前后端 UI/错误文案全量国际化；类型安全（前端编译期校验键、后端英文 msgid fallback 可读）；按需加载语言包，非默认语言零初始开销；ContextVar 方案对存量 router 侵入小（无需改函数签名传 request）。
- **负面**：新增文案需同步维护 zh/en 两份资源；`gen_i18n_po.py` 的映射表需随新增 msgid 手动扩充；ContextVar 不跨线程，后台线程/异步任务内的用户可见串需显式传 locale（当前策略是这类串不翻译或在前端渲染）。
- **验证**：前端 `vue-tsc` + `vite build` 通过（15 语言模块独立分包）；后端 `_()` 中英切换与 `{占位符}` 格式化端到端验证通过；冒烟测试 58/60 通过（2 个失败为 core 声纹匹配既有问题，与 i18n 无关）。
