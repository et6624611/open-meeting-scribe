# ADR-0008 AI 操作结果必须经系统校验

- 状态：Accepted
- 日期：2026-09-05
- 关联：`app/routers/chat.py`、`docs/ARCHITECTURE.md`

## 背景

会议助手的回复由 LLM 自由生成。v1.x 早期版本中，数据修改类请求（如「待办中参会人A应该是参会人B」）没有执行通道：LLM 拿到待办清单后凭空声称「已修正、纪要已同步更新」，而后端从未写入、前端也不刷新，幻觉操作声称直接呈现给用户，且与界面真实状态矛盾。

## 决策

**执行权与叙述权分离，操作结果以系统校验为唯一事实源：**

1. **AI 无执行权**：LLM 不直接修改任何数据。数据修改请求由一次低温度 LLM 调用解析为结构化操作（白名单：待办责任人/内容/完成状态/删除四类），`todo_id` 必须取自当前清单，越权操作在 `_sanitize_edit_ops` 被过滤。
2. **后端统一执行 + 磁盘回读校验**：`_execute_and_verify_edits` 执行操作、落盘后**回读磁盘文件逐条确认生效**，产出带 `verified` 标记的变更清单。未通过回读的变更标记为校验失败。
3. **叙述接地**：校验清单以「系统动作执行结果（已验证，唯一事实）」块注入提示词，LLM 只允许转述该块；系统提示词设「操作权限边界」为最高优先级规范。
4. **事后审计兜底**：`_audit_reply_claims` 扫描回复中的操作声称词（已修正/已更新/已删除…）。有变更 → 回复尾部追加「✅ 系统校验」执行结果清单；无变更却含声称 → 追加「⚠️ 系统校验：本轮未执行任何写操作」提示。审计结论由系统生成，不依赖 LLM 自觉。
5. **界面同步**：响应携带 `verified_changes`，前端据此刷新待办 Tab 与本地任务缓存，界面与真实状态一致。

## 取舍

- **代价**：编辑类消息多一次 LLM 意图解析调用（门槛关键词预过滤控制成本）；回复尾部校验块增加篇幅。
- **收益**：操作声称可证伪、可追溯（joblog 记录变更与校验数）；幻觉声称即使发生也会被系统结论当场纠正。
- **备选否案**：仅靠提示词约束（不可靠，LLM 仍会幻觉）；完整 function-calling 工具协议（改动面过大，v1 待办编辑场景白名单已足够）。

## 适用边界

- 当前白名单仅覆盖待办四类编辑；新增可编辑对象须同步扩展操作白名单、执行器与校验逻辑。
- 校验以磁盘回读为准；若未来存储层变更（如换数据库），校验点需同步迁移。
