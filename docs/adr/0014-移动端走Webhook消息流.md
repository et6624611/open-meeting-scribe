# ADR-0014 移动端走 Webhook 消息流

- 状态：Accepted
- 日期：2026-09-12
- 相关：`core/notify.py`、`app/routers/mobile.py`、`docs/design/MOBILE_DESIGN.md`

## 背景

用户需要在手机上实现三个功能：会议状态查看与监控、随记、会议超时检测提醒。

项目定位是开源、本地数据·云端智能，不提供官方云服务器。服务运行在用户本地电脑，手机与服务可能不在同一网络。传统移动端方案（独立 App、PWA）需要解决跨网络可达性和推送通道两个问题，在开源无云场景下复杂度高。

## 选项

1. **独立移动端面板（PWA / 响应式前端）** —— 体验完整，但需解决跨网络访问（公网 IP / 内网穿透）和推送通道（Web Push 在 iOS 兼容性差）问题，开发成本高
2. **原生 App（Swift / Kotlin / Flutter）** —— 体验最好，但开发维护成本极高，违背「轻量可部署」原则
3. **Webhook 消息流** —— 用户自选消息应用（Telegram / Bark / ntfy / 企业微信等）作为交互界面，服务通过 HTTP POST 推送通知，通过通道上行能力接收用户指令。零运营成本，不依赖官方服务器

## 决定

采用 **Webhook 消息流**方案。

核心理由：
- 零基础设施成本，项目方不运营任何服务器
- 用户完全掌控，自选通知通道，不强绑特定平台
- 复用现有后端 API（`chat.py`、`notes.py`、`tasks.py`），后端几乎零改动
- 延续项目已有的 proxy 模式（sms-proxy / asr-proxy），用户自行配置

引入**会话锚点**模型解决多会议上下文问题：服务侧维护 `active_task_id`，用户通过 `@会议名` 前缀或 `/switch` 指令切换当前交互绑定的会议。告警消息始终带会议标签，不受锚点限制。

推荐首选 Telegram Bot 作为交互通道：天然双向、免费、无需公网 IP（long polling）、支持 Markdown 和 inline keyboard。

## 后果

- 正面：
  - 4 天内可完成 MVP，开发成本低
  - 用户无需安装额外 App，用已有的消息应用即可
  - 推送通道可选，不锁定单一供应商
  - 与桌面端 AI 面板共享后端逻辑，无重复开发

- 负面 / 代价：
  - 交互体验受限于消息应用的 UI 能力（无富文本编辑器、无实时转写流）
  - 需要用户手动配置 Webhook / Bot Token（有一定门槛）
  - 单向通道（如 Server酱、Bark）只能收通知，不能交互

- 后续需注意：
  - 若用户对移动端交互需求增强（实时转写、富文本编辑），再考虑 PWA 方案作为补充
  - 会话锚点为进程级状态，服务重启后丢失（可接受，与 `realtime_*` 字典一致）
  - 上行消息需做长度限制和注入防护
