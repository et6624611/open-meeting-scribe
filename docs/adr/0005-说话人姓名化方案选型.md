# ADR-0005 说话人姓名化方案选型

- 状态：Accepted
- 日期：2026-09-03
- 相关：core/speakers.py、core/pipeline.py、core/summarize.py
- 依赖：ADR-0001（v1 纯云方案）、ADR-0002（paraformer-v2 说话人分离）

## 背景

DashScope paraformer-v2 转写结果仅返回 `speaker_id`（0/1/2…），纪要中显示为「说话人0」「说话人1」，无法直接识别发言人身份。需要将 `speaker_id` 映射为真实姓名，提升纪要可读性。

## 选项

### 1. 声纹注册（WeSpeaker）

**原理**：提取音频声纹向量，与预注册声纹库比对，自动匹配姓名。

**优势**：
- 全自动，无需人工干预
- 识别准确率高（声纹特征唯一）

**劣势**：
- 需本地部署 WeSpeaker 模型（~1GB），与 v1 纯云方案冲突
- 需注册声纹采集流程（用户需录制参考音频）
- 实现复杂度高，开发周期长

**结论**：v2 考虑，v1 不采用。

### 2. 人工映射 + 历史复用

**原理**：
- 用户手动绑定 `speaker_id` 与姓名（如「说话人0 = 张三」）
- 映射关系持久化到 `data/speakers.json`
- 后续会议自动复用已有映射（同一批人开会时免重复配置）

**优势**：
- 零依赖，无需本地模型
- 实现简单，开发周期短
- 符合 v1 纯云方案定位
- 用户可控，映射关系透明

**劣势**：
- 首次会议需手动配置
- speaker_id 变化时需重新映射（ASR 不保证同一人在不同会议中 ID 一致）

**结论**：v1 采用。

### 3. LLM 辅助识别

**原理**：将对话内容传给 LLM，让模型根据上下文推断发言人身份（如「我是张三」「请王经理发言」）。

**优势**：
- 无需额外配置
- 可从对话内容自动提取

**劣势**：
- 依赖对话中明确提及姓名
- 推断结果不可控，可能产生幻觉
- 增加 LLM 调用成本

**结论**：可作为增强功能，不作为主方案。

## 决定

**采用「人工映射 + 历史复用」方案**。

核心设计：
1. **说话人档案**：`data/speakers.json` 存储全局说话人列表（姓名、角色、备注）
2. **会议映射**：每次会议记录 `speaker_id → 说话人` 的映射关系，随纪要一起保存
3. **复用机制**：新会议开始时，展示历史说话人列表供快速选择；同一批人开会时可一键复用上次映射
4. **管线集成**：转写后自动应用映射，纪要提示词中传入发言人姓名，输出使用真实姓名

| 文件 | 变更 |

## 后果

- 正面：零依赖实现姓名化；用户可控；历史复用降低重复配置成本；符合 v1 纯云定位。
- 负面：首次会议需手动配置；speaker_id 跨会议不一致时需重新映射。
- 后续可探索：① LLM 辅助识别作为补充；② v2 引入声纹注册实现全自动。
