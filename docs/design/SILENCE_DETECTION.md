# 录音静默检测与用户存在性感知方案

## 1. 问题背景

用户反馈：录音过程中离开两小时，系统持续录制并生成原文，造成 API 配额与存储资源浪费。

根本原因：当前录音流程（`core/audio.py` → `app/routers/record.py` → `core/realtime_asr.py`）一旦启动，**没有任何机制判断用户是否仍在场**，录音会无条件持续直到用户手动停止。

## 2. 两层音频检测机制及其局限

### 2.1 第一层 — RMS 音量阈值判定静默

**原理**：在 `pcm_callback` 中计算每帧 PCM 数据的 RMS dB 值，低于阈值（如 -45 dB）则视为"静默帧"。

**失效场景 — 嘈杂环境**：

| 环境 | 典型背景噪声 RMS dB | 是否超过 -45 dB 阈值 |
|------|---------------------|----------------------|
| 安静卧室 | -55 ~ -50 dB | 否 ✅ 可检测 |
| 安静办公室 | -42 ~ -35 dB | 是 ❌ 无法检测 |
| 开放式办公室（有人交谈） | -30 ~ -20 dB | 是 ❌ 无法检测 |
| 咖啡厅 / 街道 | -25 ~ -15 dB | 是 ❌ 无法检测 |
| 空调 / 风扇持续运转 | -38 ~ -28 dB | 是 ❌ 无法检测 |

**失效原因**：背景噪声的能量持续高于静默阈值，系统永远无法将当前状态判定为"静默"。RMS 是宽带能量指标，**无法区分人声与噪声**。

> 注：理论上可通过 VAD（语音活动检测）模型替代简单 RMS 阈值来解决，但这引入额外依赖与计算开销，且对非稳态噪声（如间歇性键盘声、打印机）仍不可靠。

### 2.2 第二层 — 静默时长累计触发提醒 / 关停

**原理**：连续 N 秒被第一层判定为"静默"后，触发提醒（第一阶段）或自动关停（第二阶段）。

**失效原因**：第二层完全依赖第一层的输出。当第一层因噪声而无法识别静默时，静默计时器永远不会启动，提醒和关停机制形同虚设。

### 2.3 结论

纯音频层面的检测在嘈杂环境下存在**结构性盲区**——它只能回答"有没有声音"，无法回答"有没有人在说话"或"用户是否还在电脑前"。必须引入**独立于音频的第三层检测**。

## 3. 第三层检测 — 基于软件状态的用户存在性感知

### 3.1 设计原则

- **独立运行**：不依赖音频层结果，可独立触发提醒与关停
- **多信号交叉验证**：单一信号不可靠，需组合判断
- **保守策略**：宁可晚检测、不可误关停；误报成本远高于漏报
- **用户主权**：最终决定权在用户，系统只提醒不擅断

### 3.2 可用信号来源

#### 前端可采集的信号

| 信号 | 采集方式 | 可靠性 | 说明 |
|------|----------|--------|------|
| **页面可见性** | `document.visibilitychange` 事件 + `document.visibilityState` | 高 | 标签页切到后台时 `visibilityState = 'hidden'`，浏览器原生 API，无法伪造 |
| **窗口焦点** | `window.blur` / `window.focus` 事件 | 中 | 窗口失去焦点不等于用户离开（可能在用其他工作应用），但持续无焦点是强信号 |
| **用户交互** | `click` / `keydown` / `scroll` / `touchstart` 事件 | 高 | 最直接的在场证据；但"在看手机"时确实没有交互 |
| **WebSocket 连接状态** | `ws.onclose` / `ws.onerror` | 高 | 连接断开意味着用户关闭了页面或离开了应用 |
| **自定义心跳** | 前端定时发送 `heartbeat` 消息到后端 | 高 | 心跳中断 = 前端已无法运行（页面关闭 / 浏览器崩溃 / 设备休眠） |

#### 后端可观测的信号

| 信号 | 观测方式 | 可靠性 | 说明 |
|------|----------|--------|------|
| **WebSocket 连接存活** | `websocket_transcript()` 连接状态 | 高 | 连接断开即前端不在线 |
| **心跳超时** | 后端记录每个 task 的最后心跳时间 | 高 | 超过 N 秒未收到心跳，前端大概率已不可达 |
| **音频活动度（ASR 输出）** | `on_sentence_end` 回调频率 | 中 | 长时间无定稿句子 → 可能无人说话（但嘈杂环境下 ASR 也可能产出垃圾文本） |

### 3.3 存在性评分模型

采用**衰减计分制**，而非简单的布尔判断：

```
presence_score(t) = max(0, presence_score(t-1) - decay_rate) + interaction_boost
```

**参数定义**：

| 事件 | 分数变化 | 说明 |
|------|----------|------|
| 用户交互（click/scroll/keydown） | +100（重置到满分） | 最强在场信号 |
| 页面从 hidden → visible | +80 | 用户切回标签页 |
| 窗口从 blur → focus | +60 | 用户切回窗口 |
| 心跳到达 | +20 | 前端仍在运行（弱信号） |
| 每秒自然衰减 | -1 | 分数随时间缓慢衰减 |
| 页面进入 hidden | 立即 × 0.3 | 标签页切到后台，分数大幅衰减但不归零 |
| 窗口失去焦点 | 立即 × 0.5 | 窗口失焦，分数中度衰减 |

**满分**：100

**判定阈值**：

| 分数区间 | 判定 | 动作 |
|----------|------|------|
| ≥ 40 | 用户在场 | 无动作 |
| 20 ~ 39 | 用户可能离开 | 若同时音频层也无有效语音 → 发送提醒 |
| < 20 | 用户大概率已离开 | 发送紧急提醒，启动自动关停倒计时 |
| 心跳超时（>90s 无心跳） | 前端不可达 | 直接触发自动关停（无需等评分衰减） |

### 3.4 与音频层的协作关系

```
┌─────────────────────────────────────────────────────────┐
│                    决策矩阵                              │
├──────────────────┬──────────────┬───────────────────────┤
│                  │ 音频层：有语音 │ 音频层：无语音/静默    │
│                  │ （近 N 分钟）  │                       │
├──────────────────┼──────────────┼───────────────────────┤
│ 存在性评分 ≥ 40  │ 正常录制     │ 正常录制               │
│ （用户在场）      │              │ （可能在听/思考）       │
├──────────────────┼──────────────┼───────────────────────┤
│ 存在性评分 20~39 │ 正常录制     │ ⚠️ 发送提醒            │
│ （可能离开）      │ （用户在看）  │ "检测到无语音且页面     │
│                  │              │  不活跃，是否继续？"    │
├──────────────────┼──────────────┼───────────────────────┤
│ 存在性评分 < 20  │ 正常录制     │ 🔴 紧急提醒 + 倒计时    │
│ （大概率离开）    │ （用户在看    │ "即将自动停止录制"      │
│                  │  其他内容）   │                       │
├──────────────────┼──────────────┼───────────────────────┤
│ 心跳超时         │ 心跳超时 → 无论音频状态，直接自动关停   │
│ （前端不可达）    │ （前端已不可达，录制无意义）           │
└──────────────────┴──────────────┴───────────────────────┘
```

**关键设计决策**：

1. **音频层有效语音可完全覆盖存在性低分**：即使用户长时间不操作（评分衰减到 < 20），只要麦克风检测到有效语音，就认为用户仍在场（可能在讨论中未看屏幕）。这避免了"开会讨论中看手机被误关停"的场景。
2. **心跳超时是硬条件**：无论音频层状态如何，心跳超时（前端不可达）直接关停。因为前端已不可达时，即使录到声音也无意义——用户无法看到结果。
3. **嘈杂环境下的兜底**：当音频层因噪声失效时，存在性评分独立运行。用户离开后不再操作电脑 → 评分衰减 → 结合 ASR 长时间无定稿句子 → 触发提醒。

### 3.5 ASR 活动度辅助判断

作为音频层的补充（不依赖 RMS 阈值），后端追踪：

- **最后定稿句子时间**（`last_sentence_time`）：`on_sentence_end` 回调时更新
- **连续无定稿时长**（`silent_since_asr`）：`now - last_sentence_time`

当 `silent_since_asr > 5 分钟` 时，视为"ASR 层无有效语音活动"。

> 为何用 5 分钟而非更短：ASR 在嘈杂环境下可能产出垃圾句子，也可能在两人对话间隙长时间无输出。5 分钟是保守值，平衡误报与漏报。

### 3.6 提醒与关停策略

#### 阶段一：温和提醒（存在性评分 < 20 且 ASR 无活动 > 5 分钟）

- 后端通过 WebSocket 推送 `presence_warning` 消息：
  ```json
  {
    "type": "presence_warning",
    "level": "gentle",
    "silent_minutes": 7,
    "countdown_seconds": 120
  }
  ```
- 前端弹出非模态横幅（类似现有的 `volume_warning` 样式）：
  > "已 7 分钟未检测到语音，且页面暂无操作。是否继续录制？"
  > [继续录制] [停止录制]
- 倒计时 120 秒，用户可点击"继续录制" dismiss 提醒并重置评分

#### 阶段二：紧急提醒（阶段一触发后 2 分钟无响应）

- 推送 `presence_warning` with `level: "urgent"`：
  ```json
  {
    "type": "presence_warning",
    "level": "urgent",
    "countdown_seconds": 60
  }
  ```
- 前端弹出模态对话框（必须交互才能 dismiss）：
  > "录制已持续无活动 9 分钟，将在 60 秒后自动停止。"
  > [继续录制] [停止并保存]

#### 阶段三：自动关停（阶段二触发后 60 秒仍无响应）

- 后端自动调用停止录制流程（等同于用户点击"停止录制"）
- 已录制的内容正常保存并进入管线处理
- 推送 `auto_stopped` 消息（若 WebSocket 仍存活）：
  ```json
  {
    "type": "auto_stopped",
    "reason": "user_presence_timeout",
    "duration": 540,
    "message": "因长时间无活动已自动停止录制"
  }
  ```

#### 心跳超时的特殊处理

- 心跳中断 > 90 秒 → 不经过三阶段提醒，直接自动关停
- 原因：前端已不可达，提醒无法送达，继续录制无意义
- 若 WebSocket 也断开，则在后端直接执行停止流程

### 3.7 误判防护

| 场景 | 风险 | 防护措施 |
|------|------|----------|
| 用户在看屏幕但不操作（开会讨论中） | 存在性评分衰减 → 误提醒 | **音频层有效语音覆盖**：只要 ASR 持续产出定稿句子，即使评分 < 20 也不触发提醒 |
| 用户切到其他标签页做笔记 | 页面 hidden → 评分衰减 | **短暂切走不触发**：评分从 100 衰减到 20 需要约 80 秒（衰减率 1/s + hidden 乘 0.3），短时间切走影响有限 |
| 网络抖动导致心跳短暂中断 | 误判为前端不可达 | **心跳超时设 90 秒**：容忍短暂网络波动；WebSocket 本身有重连机制 |
| 嘈杂环境 ASR 产出垃圾句子 | 误认为有人说话 | **垃圾句子过滤**：ASR 定稿句子若为纯标点/单字/重复内容，不计入"有效语音活动" |
| 用户主动挂机（知道会浪费但不在乎） | 被反复提醒打扰 | **提醒频率限制**：同一录音会话最多提醒 2 次（温和 + 紧急各一次），之后不再提醒，直接关停 |

## 4. 可配置参数

所有阈值均通过 `data/settings.json` 的 `silence_detection` 字段配置，前端设置页提供 UI 调节入口。

```json
{
  "silence_detection": {
    "enabled": true,
    "presence": {
      "score_max": 100,
      "score_decay_per_sec": 1,
      "score_interaction_boost": 100,
      "score_visibility_return": 80,
      "score_focus_return": 60,
      "score_heartbeat": 20,
      "score_visibility_hidden_multiplier": 0.3,
      "score_blur_multiplier": 0.5,
      "threshold_warning": 20,
      "heartbeat_interval_sec": 30,
      "heartbeat_timeout_sec": 90
    },
    "audio": {
      "rms_silence_db": -45,
      "asr_no_sentence_timeout_sec": 300
    },
    "action": {
      "gentle_warning_delay_sec": 0,
      "gentle_countdown_sec": 120,
      "urgent_countdown_sec": 60,
      "max_warnings_per_session": 2
    }
  }
}
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `enabled` | `true` | 是否启用静默检测（可在设置页关闭） |
| `score_max` | `100` | 存在性评分满分 |
| `score_decay_per_sec` | `1` | 每秒自然衰减量 |
| `score_interaction_boost` | `100` | 用户交互（click/scroll/keydown）后重置到的分数 |
| `score_visibility_return` | `80` | 页面从 hidden → visible 时增加的分数 |
| `score_focus_return` | `60` | 窗口从 blur → focus 时增加的分数 |
| `score_heartbeat` | `20` | 每次心跳到达增加的分数 |
| `score_visibility_hidden_multiplier` | `0.3` | 页面进入 hidden 时分数乘以此系数 |
| `score_blur_multiplier` | `0.5` | 窗口失焦时分数乘以此系数 |
| `threshold_warning` | `20` | 触发提醒的评分阈值 |
| `heartbeat_interval_sec` | `30` | 前端心跳发送间隔（秒） |
| `heartbeat_timeout_sec` | `90` | 心跳超时阈值（秒），超时直接关停 |
| `rms_silence_db` | `-45` | 第一层 RMS 静默判定阈值（dB） |
| `asr_no_sentence_timeout_sec` | `300` | ASR 无定稿句子超时（秒），5 分钟 |
| `gentle_countdown_sec` | `120` | 温和提醒后的自动关停倒计时（秒） |
| `urgent_countdown_sec` | `60` | 紧急提醒后的自动关停倒计时（秒） |
| `max_warnings_per_session` | `2` | 单次录音最大提醒次数 |

## 5. 实现架构概览

### 5.1 后端（`app/routers/record.py`）

```
pcm_callback()
  ├── 更新 last_pcm_time（每次回调）
  ├── 计算 RMS dB（现有逻辑扩展）
  ├── 更新 last_sentence_time（on_sentence_end 回调时）
  └── 后台监测协程（每 10 秒检查一次）
        ├── 检查心跳是否超时 → 直接关停
        ├── 检查 presence_score（从前端心跳中推算）
        ├── 检查 asr_no_sentence_timeout
        └── 触发提醒 / 关停
```

新增后台协程 `silence_monitor_loop(task_id)`，在 `start_record()` 中随录音一起启动，随录音停止而退出。

### 5.2 前端（`frontend/src/composables/useWebSocket.ts` + `RecordingView.vue`）

```
useWebSocketTranscript()
  ├── 新增：心跳定时器（每 30 秒发送 {type: "heartbeat"}）
  ├── 新增：处理 presence_warning 消息
  └── 新增：处理 auto_stopped 消息

RecordingView.vue
  ├── 新增：采集 visibilitychange / blur / focus / interaction 事件
  ├── 新增：本地维护 presence_score
  ├── 新增：每次交互 / 事件后通过心跳携带最新评分
  └── 新增：presence_warning 弹窗 UI（温和横幅 + 紧急模态框）
```

### 5.3 信号传递路径

```
前端事件                    后端
────────                    ────
click/scroll/keydown ──┐
visibilitychange ──────┤
focus/blur ────────────┤──→ 本地 presence_score 计算
                       │         │
heartbeat{score: N} ───┘         │
                                 ↓
                    silence_monitor_loop()
                      ├── 更新 task 的 presence_score
                      ├── 结合 ASR 活动度判断
                      └── 推送 presence_warning / 执行关停
```

## 6. 边缘场景覆盖

| 场景 | 音频层 | 存在性层 | 最终行为 |
|------|--------|----------|----------|
| 安静房间，用户离开 | ✅ RMS 低于阈值 → 静默检测生效 | ✅ 评分衰减 → 触发提醒 | 双层确认，快速提醒 |
| 嘈杂办公室，用户离开 | ❌ 噪声高于阈值 → 静默检测失效 | ✅ 评分衰减 + ASR 无有效句子 → 触发提醒 | 第三层独立兜底 |
| 嘈杂咖啡厅，有人说话但用户不在 | ✅ ASR 有定稿句子 | ✅ 评分衰减 | 音频层覆盖 → 不提醒（可能用户委托他人继续） |
| 安静房间，用户在看不操作 | ✅ RMS 低但 ASR 可能有输出 | ⚠️ 评分衰减 | 若 ASR 有输出 → 不提醒；若 ASR 也无输出 → 提醒 |
| 用户切到另一标签页做笔记 30 秒 | 不影响 | 页面 hidden 30 秒 → 评分从 100 衰减到约 50 | 不触发（阈值 20） |
| 网络断开 2 分钟 | 不影响 | 心跳超时 90 秒 → 直接关停 | 后端自动停止录制 |
| 浏览器崩溃 | 不影响 | 心跳中断 + WS 断开 → 直接关停 | 后端自动停止录制 |

## 7. 与现有功能的兼容

- **暂停/恢复**：暂停录音时，存在性检测暂停（不计算衰减）；恢复时重置评分到满分
- **孤儿恢复**：服务重启恢复孤儿录音时，重新初始化存在性检测（评分满分）
- **设置页**：新增"静默检测"开关与参数调节入口（高级设置区）
- **国际化**：所有新增提示文案支持中英文（`recording.json` 新增 `presence_warning` 等 key）
