# 需求记录：决策中心使用反馈迭代（REQ-DECISION-CENTER-R2）

## 1. 背景与证据核验

决策中心（DC-DEC-B1/F1）2026-09-25 项目方浏览器点验通过后，项目方提出五条使用意见 + 一条冗余观察。管理员逐条对照 main 代码核实（行号已确认）：

| # | 项目方反馈 | 代码证据 | 核验结论 |
|---|---|---|---|
| 0 | 分组视图下卡片底部重复显示会议名称，信息冗余 | 组头已显示会议标题（`DecisionCenterView.vue:82`），卡片 meta 行又显示来源会议标题+日期+知识库（`DecisionCard.vue:29-41`） | **属实**，组内卡片「来源会议」文本冗余 |
| 1 | 应支持在决策中心内直接操作，避免跳转至会议纪要才能修改 | 卡片操作菜单仅「已被取代/已撤销」两项（`DecisionCard.vue:17-24`），**无编辑文本、无删除**；修改只能跳纪要页改 markdown（且 §11-3 已裁决不回同步） | **属实**，决策中心缺行内编辑/删除能力 |
| 2 | 平铺与按会议分组无明显视觉区分，平铺失去意义 | 切换器存在（`DecisionCenterView.vue:12-15`）；两视图卡片同为 `DecisionCard`，差异仅组头折叠条 | **属实**，区分度低 |
| 3 | 补录弹框输入内容与会议纪要需输入的内容不一致 | 弹框字段 = 归属会议 + 决策文本 + 待确认勾选（`AddDecisionDialog.vue:13-35`）；纪要「主要结论」= 编号列表文本 + `[待确认]` 前缀 | **字段表面一致，具体不一致点待项目方澄清**（见 §4-O1） |
| 4 | 筛选中的知识库未支持检索 | 知识库筛选为原生 `<select>` 下拉（`DecisionCenterView.vue:32-36`），无输入过滤 | **属实**，知识库多时难以定位 |
| 5 | 状态能否自定义：改写名称、新增状态、排序、颜色标注 | 状态为封闭枚举 `active/superseded/revoked` + `pending` 标志（模型层 `task["decisions"].status`），前端文案走 i18n 固定键，颜色写死样式表 | **现状不可自定义**；全自定义会破坏语义锚点，需分级裁决（见 §4-O3） |

## 2. 目标

在不改变决策数据模型核心语义（R1）与跨会议聚合 API（R2）的前提下，按项目方使用反馈迭代决策中心交互：**去冗余、免跳转编辑、去无效切换、补录口径对齐、知识库可检索、状态呈现可配置**。

## 3. 范围（候选交付项）

### F1 — 分组卡片去冗余（对应反馈 0，无争议，直接列实施）

- 分组视图组内卡片 meta 行不再显示来源会议标题文字；日期/知识库徽标保留与否随视觉稿定。
- 保留跳转纪要能力，降级为图标按钮或悬停操作（设计细节归实施稿）。

### F2 — 移除「平铺/分组」切换（对应反馈 2，无争议，直接列实施）

- 删除视图切换器（`dc-seg`），列表固定为按会议分组视图；`view_flat` 相关 i18n 键与代码清理。

### F3 — 决策中心行内直接操作（对应反馈 1；范围含反馈 0 的跳转诉求）

- 卡片操作菜单新增：**编辑决策文本**、**删除决策**。
- 编辑/删除走既有任务级 CRUD API（`PUT/DELETE /api/tasks/{task_id}/decisions/{id}`），无新接口。
- 决策中心内编辑**不回写纪要正文**——与原 REQ-DECISION-CENTER §11-3「漂移手动修正」裁决同构，无需重开。
- 待裁决：「在决策中心操作会议纪要」是否还包含更多操作（如查看决策上下文摘录）→ §4-O2。

### F4 — 补录弹框口径对齐（对应反馈 3，**阻塞在澄清**）

- 待项目方说明具体不一致点后定义；不预写方案。

### F5 — 知识库筛选支持检索（对应反馈 4，无争议，直接列实施）

- `<select>` 升级为可输入过滤的 combobox（键入即筛选项，键盘可选中）；保留「全部 / 未归属」特殊项。

### F6 — 决策状态可配置（对应反馈 5，**分级方案待裁决**）

现状语义锚点（不可动摇部分）：

- `active` = 生效中，参与默认筛选与沉底分流；`superseded`/`revoked` = 失效类，沉底折叠；`superseded` 驱动取代链接；`pending_confirmation` 驱动「待确认」徽标。
- 抽取、回填、取代、筛选、验收全部按该枚举运作；存量数据 359 条决策已落此模型。

**方案甲（呈现层自定义，成本低）**：开放状态**显示名改写、颜色标注、筛选项排序**配置；枚举语义与集合不变。改动 = 前端配置 + 少量设置持久化。

**方案乙（真·自定义状态，成本/风险高）**：允许新增业务状态（如「执行中」「已验收」），需要：状态字典数据层、决策模型 `status` 从枚举改引用、聚合 API 筛选参数改造、新旧状态与生效/失效两分法的映射规则、抽取/回填默认值定义、i18n 键改造、4 项既有 AC 重写。决策链完整状态机（原 §5 明确排除审批流/权限分级）是否借本单解冻，需项目方拍板。

- 管理员建议：**先甲后乙**——本轮落甲（覆盖"改名、颜色、排序"三项诉求），"新增状态"单列为乙评估项，待真实使用场景（谁、什么链、几个状态）反馈再裁决。

## 5. 验收标准（草案，随裁决定稿）

1. 分组视图内卡片不再出现与组头重复的会议名称；跳转纪要能力仍可用。
2. 页面顶部无「平铺/分组」切换器，列表按会议分组呈现。
3. 决策卡片菜单可编辑文本并可删除，编辑后列表与来源徽标即时刷新；`auto` 来源决策被删除后重新生成纪要不复活（`source` 语义验证）。
4. 知识库筛选键入 ≥ 2 字符可过滤选项并选中生效（待 O1 关闭后补补录弹框口径 AC）。
5. 状态显示名/颜色/排序可在设置中修改并全局生效（徽标、筛选 chips、卡片）；系统默认状态行为不变。
6. 浏览器验收包按新验收流交付（分步验证脚本 ≤5 步 + 自测截图）。
